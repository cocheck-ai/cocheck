# Host hook adapter

`src/hook.ts` lets a host's own hooks feed CoCheck's review page, with no cooperation from the agent. The installer wires the hooks into each host's own config by default (see "Which hosts get wired"), and a session records nothing until it starts tracking. Each hook call is a short-lived process: it reads one payload, updates the state files and the ledger, and exits.

## What it does

The adapter keeps every file of the task folder, of any type, as whole stored states in the task's store, `$COCHECK_HOME/tasks/<id>/states/<sha256>`; its small state file is under `$COCHECK_HOME/hooks/<key>/`. Only editor scratch files (`~$*`, `.~lock.*#`, `._*`, `.DS_Store`, `~WRL*.tmp` and CoCheck's own review export) are left out, and so is the `.cocheck` folder at the top of the task folder. The CLI picks the task folder from `--folder` of the hook command, else the folder `cocheck track start` recorded for the session, else the host's folder variable (`CLAUDE_PROJECT_DIR` for Claude Code), else, for Codex and Copilot, the payload's `cwd` when it is absolute. The adapter itself only ever sees that folder, never the payload's `cwd`, so an agent that `cd`s into a subfolder keeps one baseline. The key is that folder and the host, not the session: two sessions in one folder share one observation state (copies, baselines, open calls, one lock), and each session's work is written to its own task. The adapter only stores states and reads no file for what changed inside it: for a file a connector claims (the built-in Office connectors claim Excel, Word and PowerPoint files), the review process asks the connector for the change list from the two stored sides.

**Per-step file state.** A step is one ledger row (`steps`) written by every sweep that changed a file, in the same flush as the ops of the calls open at that sweep. Its autoincrement id is the key ops, states, prompts and narration point at; an op lists the ids of the steps found while its call was open in `steps`. `state.seq` stays the idempotency key of the op writes only. Each changed file at each step is one state event (`file_states`): the file, its SHA-256, the previous SHA-256, Pre, Post or Stop, the calls open, the calls credited with the change, its size, whether the bytes were kept (`whole`, `hash` or `gone`) and a note in words when the state is not an ordinary whole copy. The bytes are copied once per hash into the task's store. Every file in the folder is copied at the task's first event, under the scan caps or, for files a connector reads, under their own allowance. Each sweep stat-filters (size, mtime, ctime, inode) and copies only what moved; ctime cannot be set by a program, so a write that restores mtime still moves it and is credited to the call that was open; a full hash is taken at Stop and at the Pre and Post of a call whose input names the file, so a writer that moved none of the four is still seen, at the latest at Stop. A call being open at a sweep is not credit: each state event lists the calls open and, separately, the calls credited (`credited_json`; the baseline and a change found with no call open credit nobody). Symbolic links in the folder are never followed: a link is not tracked, and a tracked file replaced by a link is recorded as gone with that reason in words, so bytes outside the folder never reach the store. The task's `tasks/<id>` and `states` folders are 0700. Caps, each written on the state event or in `state_removals` in plain words: above 25 MB a file keeps its first and its current state, and the states between are deleted and keep their hashes; past 1 GB per task the states between each file's first and current one are deleted first (files no connector reads go first, largest first, and files a connector reads go last, oldest first), then first and current states (files no connector reads first, then files a connector reads, largest first each time; the current state of a file a connector reads is kept until its next state is saved), and only hashes are kept; at the start of the task, files no connector reads are copied under the scan caps (500 files, 200 MB, in name order) and files a connector reads under their own allowance (2,000 files, 1 GiB), and a file past its cap is fingerprint only; if it changes later, the new state is copied whole under the per-file and per-task caps above. Several writes inside one call show as the file before the call and after it.

**The whole tree.** Every sweep lists the watched folder recursively, so a file in a subfolder is a state like any other: the stat filter, the Stop hash and the caps keep their meaning over the tree, and the 500 files and 200 MB caps count across all of it (a file past them is fingerprint only at the start of the task, with the reason on its state event; a later change to it is copied whole under the per-file and per-task caps). The walk lists at most 100,000 entries and then stops, and the record says so. A state event's file is the absolute path in the ledger; the notes name it relative to the folder. Any folder starts a task, whatever files it holds, an empty one included. Files a connector reads have their own allowance and never use up the 500 files and 200 MB; no file type is sorted ahead of another. Not entered: `.git`, `.hg`, `.svn`, `node_modules`, `.venv`, `venv`, `__pycache__`, `.tox`, `.cache` at any depth, any Python environment (found by its `pyvenv.cfg` or `conda-meta`), and the CoCheck data home when it sits inside the folder. Each skipped folder is said once, as an op of its own (`hookEvent: "Skip"`, `skipped: [{folder, note}]`, with the folder relative to the watched folder) in words. Symbolic links are never followed at any depth: a link is not tracked, and a tracked file whose own path, or a folder above it, is replaced by a link is recorded as gone with that reason. Secret files, by name at any depth (`.env` and `.env.*`, `*.pem`, `*.key`, `*.keystore`, `*.jks`, `*.token`, `service-account*.json`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `credentials*`, `secrets.*`, `.npmrc`, `.netrc`, `.pypirc`; any letter case): the file is read only to take its SHA-256, so no byte of it is copied to the store (its state is `kept: "hash"`); each change, creation or deletion is a state event with the hash and size and the note `A secret file was changed: <relative path>`. A secret file does not count against the scan caps. The name rule is `SECRET_NAMES` and `isSecretPath` in `src/secret-files.ts`, and a renamed file is judged by its new name. A text file of any name whose contents hold a value a secret rule finds (`secretRuleInBytes` in `src/secret-scan.ts`) is also kept as its hash and size only.

**How long the store lives.** Across rounds. At sign-off the states between each file's first and final state are deleted; the first and final stay until the 30-day value expiry, then they are deleted too. A task that is never signed off ends at the 7-day idle expiry, which deletes its store. The ledger keeps the hashes and the events either way.

**Attribution rule (safe direction first).** A change is credited only to calls that are open when a sweep finds it, jointly with all of them that may have made it: at a Post (or PostToolUseFailure) and at a Pre that runs while other calls are open. A change found at a Pre with no call open, at Stop (when no helper call of the session is still open), or by a Post whose Pre was never seen (or whose call already expired) is not from an agent call: no op names it and the round shows it `unlogged`. The record never says a person made it. Credit is also narrowed by evidence (`src/credit-guard.ts`, `src/attribution/`): a call whose result is already in its agent's transcript is credited by the sweep of the event that sees the result and by no later one; a call blocked by a PreToolUse hook or denied is credited with nothing; a call whose work can outlive its result (a background job, `&`, `nohup`) is not closed that way; a tool that cannot write (WebFetch, WebSearch, ToolSearch, Skill, TodoWrite, read-only MCP tools, besides Read, Glob, Grep and SendMessage) is never credited; a Write or Edit credits only its own `file_path`; and a call whose child ran a tagged write is credited with that write. The list of calls open is never narrowed: a change no open call may claim reads "during agent calls".

- **PreToolUse** sweeps (diffs every changed file against its last stored state and stores the new one), gives what moved to the calls already open (or, with none open, treats it as not from an agent call), and opens the call. It also baselines a file a connector reads that the call's input names outside the folder, when outside watching is on.
- **PostToolUse / PostToolUseFailure** sweep and log one op per call: the host's tool name, `tool_use_id`, and the command plus description as the intent. The op names the files the call changed, never cells (`Entry`, `src/hook-adapter.ts:314`: the connector that reads a claimed file says what changed inside it). A call that changes nothing logs an op with no files. Both events close the call, except a Claude Code Bash call with `run_in_background`, which stays open until Stop or expiry.
- **Overlapping calls** share every change a Post finds while they overlap. Each op lists all of them in `jointWith` and in its intent; none is picked.
- **Expiry.** A call still open 10 minutes after its Pre is closed and its op logged; it never shares later changes. The op's `closedAt` is when the adapter noticed the expiry (at a later event), not the open time plus 10 minutes. A Post that arrives for a call the expiry closed logs the call's real outcome in place of the expiry one and credits nothing; a Post for any other already closed `tool_use_id` logs nothing more.
- **Background jobs.** A call with `run_in_background` stays open past its Post, so what the job writes later is joint with it and with whatever else is open. After the 10-minute expiry, or after Stop, later writes are no longer tied to it.
- **Stop** sweeps, closes only the calls of its own agent (a helper's calls of the same session stay open and can still claim what moved), then cuts the round (`TaskStore.submit`). A Stop that closes a call that never got a Post gives it only what other calls' Posts gave it jointly. The existing review page shows the net change, with the per-call ops behind each row.
- **New, deleted, renamed claimed files (Office files and any other type a connector claims).** A claimed file that appears after the first event is not baselined; the round reports it as a new file, credited to the calls open when a sweep first finds it (all of them, jointly, after the credit guards below), and to no call when none is open. A file that disappears is credited as a file-level change; a rename is a delete plus a new file. Credit is per file and step, never per cell (`src/hook-adapter.ts:314`, plan H1). At the task's first event every claimed file is copied whole under its own allowance, 2,000 files and 1 GiB, apart from the general scan caps; a claimed file whose copy fails there is kept as its hash with the reason in words, and the task goes on (`src/hook-adapter.ts:512-517`, `:1750-1754`, `:1885`).
- **Half-written claimed files.** A claimed file whose bytes are cut short at a sweep (`cutShortReason`, `src/connector/claimed.ts:78`) is a state of its own: its bytes are kept, the state event says "could not read at this point", and the calls open at that sweep are credited with the file-level change (`src/hook-adapter.ts:2223-2241`). The last whole state stays the diff base and the file is read again at every sweep. When it can be read, the change goes to the calls that were open while it was cut short if its hash is the same, and is joint with the calls open now, and says so, if the hash moved.
- **Crash safety.** A sweep never deletes a stored state. State (including the steps and ops still to log) is written atomically first; only then are the steps and ops logged (each with a key, so none is logged twice) and any state a size cap dropped deleted. A kill at any step leaves the next event able to finish or redo it.

**Outside watching.** One boolean, default on: `--outside-watching on|off` in the hook command, or `COCHECK_OUTSIDE_WATCHING=off` (the flag wins; `off`, `0`, `false` and `no` turn it off). The adapter reads every path-like token a call names (path fields of the input, and the words of its strings: absolute, `~`, `.`, `..`, `./x`, `../x`, `a/b`, `*.xlsx`, redirect targets), resolves each against the working directory in effect where the token sits (the payload's `cwd`, moved by `cd`, `pushd` and `git -C` inside the command), and classifies it inside or outside the folder. A `cp`/`mv` whose destination is a directory names the source names inside it. A token built from a variable the payload cannot resolve makes the call "path unknown". On: a file a connector reads named outside the folder is baselined at PreToolUse and diffed at PostToolUse, and the paths a call names outside the folder are recorded for the page. Off: nothing outside the folder is copied, diffed or named, and an outside path in a recorded command or label becomes `[outside path]`. Path reading is a heuristic on command text: a script that writes somewhere it never names is invisible to it.

**The request.** `UserPromptSubmit` stores the user's prompt text as an op of the session's task. The first prompt of a tracked session opens the session's task, and the folder's starting copy is taken then; with a task already open, the request is written at once so a live review page shows it. A wake notification (`<task-notification>`) waits for the round's close. A prompt is cut at 8,000 characters with its full length noted, and a session keeps its last 3 unwritten prompts (an `earlier` count says how many were dropped). A round with no captured prompt says "Request not captured". A payload without prompt text is not captured. The same handler reads every host's `prompt` field.

**When the request was sent.** Each captured request carries three stamps, on the prompt op in `requests`, one entry per text in `prompts`, same order: `seq`, the number it was stamped with at submit (the one counter calls' starts also draw from; 0 when the held state predates the stamp); `at`, the wall time at submit in epoch milliseconds (`"unknown"` when the clock gave nothing usable); and `firstStep`, the ledger id of the first step written for the request, or `null`. A request written at its round's first call is told its first step later by a `RequestFirstStep` op. The timeline reads these stamps (`src/timeline/load.ts`, `runs.ts`). A call's position for ordering is its start: its op carries `startSeq`, stamped at its Pre from the same counter (the op key's own number is its close order and is only the write's idempotency key).

**Which request a call belongs to.** A call belongs to the last request its own session submitted before the call started. The Stop that cut the ledger's turn does not decide it: a helper's calls that run on after a Stop stay with the request that launched the helper, not the prompt that wakes the session later. A subagent's calls (`agent_id` on the call op) belong to the request its first call belongs to, wherever they start. A call is never under a request submitted after it started. This is read from the stamps alone (the timeline, `src/timeline/runs.ts`); a record without a `startSeq` on every call or a `seq` on every text keeps the time and step rules.

**First step after the Stop.** A step found after the Stop that ended the turn (a launched agent's) cannot be in the prompt op, so its `firstStep` can stay null in the ledger. The review fills a null `firstStep` from the steps credited to calls of the same session that started after the request and before that session's next one; a `firstStep` the hook wrote is never changed, and a request none of whose calls produced a step stays null.

**A Stop with nothing in it.** A Stop whose own sweep found no change, in a task that already has a round and no op or step since it, cuts no round: a chat-only turn would otherwise cut a round identical to the last. The first round, a Stop after a call, and a Stop that finds a change still cut one.

**Narration.** Each call's op carries `narration`: the agent's own words on the call, read from the host's session file and labelled `the agent's own words`, or `no narration recorded` (never empty text). When the Stop closes a round the session recorded, it adds one op (`hookEvent: "Stop"`, `closing`) holding the agent's final message as the round's closing claim. Narration is the agent's assistant text only. It is context for the reader: it never sets grouping, credit or row order, and it never replaces, hides, merges or reorders a row. Claude Code: the transcript is read at Pre (and again at Post), from a byte offset kept in state, up to the last complete line: the assistant text since the previous tool_use belongs to the next one. Calls in one message are parallel: the first holds the text, the others carry `sameAs` with its tool_use_id, and when the record is read (`readRecord`) such a call takes that call's words. Codex: the session rollout is found by session id under `~/.codex/sessions`; the `AgentMessage` items since the previous `CommandExecution` item (whose id is the ledger's `exec-<uuid>` call id) or the start of the turn are the call's words, and a `final_answer` is the closing claim. If the host's Stop payload carries `last_assistant_message`, that is the closing claim. Tool results and user text are never read: those lines are not even parsed. Reads are bounded: at most 256 KB and 150 ms per event; a missing, rotated, truncated, half-written, garbled or reformatted file records "no narration recorded" and never fails the hook. A call's words are cut at 2,000 characters, a closing claim at 4,000.

**What a call touched.** Each call's op carries `toolLabel` in its args: `{ fields, dropped?, withheld?, inputFields? }`, built by `src/tool-label.ts` from the tool input, the same function for every host. `fields` holds only allowlisted field names that name things. The allowlist is one table, `TOOL_LABEL_TABLE`, so a new tool is one row: Bash `command`, `description`; Read, Edit, MultiEdit, Write `file_path`; NotebookEdit `notebook_path`; Glob `pattern`, `path`; Grep `pattern`, `path`, `glob`; Skill `skill`, `name`; ToolSearch and WebSearch `query`; WebFetch `url`; Task and Agent `subagent_type`, `description` and the helper's `prompt` (its brief, cut at 6,000 characters with head and tail kept); Codex's `spawn_agent` name, type and message; SendMessage `to`, `summary` and its message text (cut at 6,000). An MCP tool (`mcp__server__tool`, a connector) and any tool with no row records its input field names only, in `inputFields`, never the value of a field; the exception is path and URL fields (`file_path`, `path`, `paths`, `notebook_path`, `url`) of an MCP tool, which are also recorded in `fields`. Never stored, because no row names them: `content`, `old_string`, `new_string`, `edits`, `body`, file bodies, patches, a WebFetch `prompt`. A URL is recorded as scheme, host and path: userinfo, query string and fragment are cut, and a value that is not a URL is dropped. Each string is cut at 200 characters (`paths` keeps at most 10). A value the secret scanner flags (the gitleaks default ruleset, `src/secret-scan.ts`) is not recorded; the field is listed in `dropped` with the reason, and a flagged helper brief or message leaves only its hash and rule family in `withheld`. A password in free prose with no vendor format is not detected. With outside watching off, an outside-folder path becomes `[outside path]`. A missing, non-object or odd `tool_input` gives an empty label and never fails the hook.

The timeline read model that turns these records into one JSON document per task is described in [timeline.md](timeline.md).

`namedFileMissRate(ledger, taskId)` (in `src/hook-adapter.ts`) returns `{changing, missed}`: calls that changed a file themselves, and those whose input did not name it.

## Safety

- `COCHECK_HOME` must be set (the installer writes it into the hook command from `--home`, which has no default), and must not be `~/.cocheck`, a symlink to it, or a path inside it (checked on the real path). Otherwise the adapter exits 1 with a message. It exits 1, never 2, on any failure: exit 2 would block the host's tool call.
- It reads files as bytes only (copies, hashes, the secret scan). It never opens an Office app and never starts a connector.
- Its stdout is empty except for two outputs. On a recorded `UserPromptSubmit` of a tracked session it prints a short context text for the agent (`src/session-context.ts`; Copilot's profile turns this off). On a Claude Code Bash `PreToolUse` it prints the attribution tag as `hookSpecificOutput.updatedInput` (`src/attribution/tag.ts`) when the tag setting allows it (`on`, or `auto` in `bypassPermissions` mode). Neither changes capture or the exit code.

## Journal and normalizer

- `src/hook-cli.ts` appends an index line for the raw stdin bytes to `<COCHECK_HOME>/journal/<session key>.jsonl`, where the key is a hash of the session id. It does this after the tracking gate (below) and before the folder, the host argument or the JSON are checked: event name, tool_use_id (or a deterministic `syn-<hash>` id with `synthetic: true`), time, byte size, sha256. Never a part of the body. One O_APPEND write per line, so concurrent hooks never tear a line. An untracked session journals nothing.
- A failure after that line writes a `failure` marker linked to it (exit 1); a completed event writes a `done` line. An event line with no `done` line and no marker is how a killed hook shows: a SIGKILL cannot write a marker.
- No raw event body is written: the journal holds `.jsonl` index lines only. Older installs left `<session>.bodies/<sha>.body` folders; a Stop that completes still deletes those of that session and of the shared `unknown` and `unparsed` buckets, and any later run deletes those of sessions idle for more than 24 hours. Index lines are never deleted.
- A journal that cannot be written changes nothing: same exit code, same ledger ops. One line on stderr and a `journal.degraded` file in the home say so.
- `src/normalize.ts` is the only code that reads a host's raw payload. `normalize(host, raw)` returns a `NormalizedEvent` (`v: 1`; an unknown version is refused); `hook-adapter.ts` consumes only that. `handleHook(rawPayload, options)` remains as a wrapper. The hosts wired are the profiles registered in `src/hosts/index.ts`: Claude Code, Codex and Copilot.

## Canonical event (v1)

The contract inside CoCheck is `NormalizedEvent` with `v: 1` (`src/normalize.ts`). Claude Code's hook payload is the shape the other hosts are mapped onto; each host's profile (`src/hosts/`) says which payload key feeds each field. `normalize(host, raw)` copies values through unchanged (never coerced), and `assertNormalized` refuses any other `v`. The adapter reads only this event.

Kinds (`EventKind`, `src/hosts/types.ts`): `tool-pre` (before a call), `tool-post` (after a call), `tool-failure` (the host's own failed-call event), `stop` (the main agent finished a turn), `subagent-stop` (a helper finished), `prompt` (the user submitted a prompt), and `other` (an event name the adapter does not act on, or one the profile's `refineKind` demotes, for example a helper's own prompt).

Per-action kinds, for a harness that reports each action on its own event instead of as a tool call (additive and optional: no host wired today maps an event to them, and the shape stays v1). `file-edit` (a file the harness changed: the path and the edits as `{ old_string, new_string }` pairs, or the file's whole new content), `shell-pre` and `shell-post` (a shell run before and after: the command, the cwd, and on the post the exit code and output when sent), `session-start` and `session-end` (recognised and carried; the adapter records nothing for them yet). A profile with `perAction` names the tool each is a call of in its own `toolClasses` and the payload keys that feed it; `normalize` then sets `toolName`, `toolInput` (`{ file_path, edits }`, `{ file_path, content }` or `{ command }`) and, for a shell post, `toolResponse` (`{ exit_code, output }`), so the credit rules read it as a call of that class. A `shell-pre` is a tool Pre and a `shell-post` a tool Post for every rule after the entry. A `file-edit` is a call whose Pre and Post happen together: the change found since the last event is credited as for any call, and it is proven (`host-reported-edit`) only when the reported edit replays on the recorded state, exactly as for a Write or Edit call.

Join rules: an event carrying the call id of a call already open in the same session is that call. A `shell-pre` with the id of an open call opens nothing; a tool Pre whose id a `shell-pre` opened opens nothing; a second Post of a closed call adds no op. A `file-edit` with the id of an open call of its session adds its edits to that call (its Post proves them); with no id, an id already used, or another session's id, it opens a call of its own (id `file-edit-<n>`, `synthetic` true) in the session that sent it. Bound: a harness whose first event in a folder is a file edit has no earlier state to replay it on, so that change is found only as already present.

Always present on the object: `v`, `host`, `kind`, `eventName` (the host's own event name; a host with `eventFromArg` is told it by the hook command's `--event`), `session` (a helper's event under its own session id carries the main session's id when the profile names a `parentSession` key), `narratesBeforeCall` (true when the host writes the call's words to its session file before the Pre), `sessionFileBySessionId` (the session file can be found from the session id alone), `extra`, `proof` and `synthetic`. `session` is typed as a string but passes through unchecked, so an odd payload yields an odd value.

Optional (undefined when the payload lacks the key): `cwd`, `toolName` (namespace removed by the profile), `toolInput` (parsed when the host sends JSON text, and scrubbed of withheld patch contents), `toolResponse` (a post event's result, kept only to scan an MCP call's response), `toolUseId`, `agentId`, `agentType`, `launchKey` (Copilot only: set by `src/copilot-helpers.ts`, never sent by the host), `failure` (`raw`, `interrupted`, and `inferred` when read from output text; present when the event reports a failed call), `transcriptPath`, `helperTranscriptPath` (only for a host that keeps a helper transcript beside the session file), `lastAssistantMessage`, `prompt`.

`extra` holds `turnId`, `permissionMode`, `model`, `stopHookActive` when the host sends them. `proof` is empty and `synthetic` is false for every host wired today.

The per-call reason is not a field of the event: it is read from the tool input at the key the profile names in `fields.callReason` (`description` for Claude Code, Codex and Copilot alike, from `SHARED_FIELDS`).

## Which hosts get wired

`cocheck install` with no `--for` wires Claude Code, Codex and Copilot (the built-in harnesses), each only if its config folder exists in the home (`~/.claude`, `~/.codex`, `~/.copilot`, or the host's own folder variable); `--for` names hosts explicitly, and a host not named or not present is never edited. The rule and the command are in [install.md](install.md). Each host's hook events, payloads and recordings are under `platforms/` (`platforms/README.md`, then `claude-code`, `codex`, `copilot-cli`, `copilot-vscode`, `cursor`, `antigravity`). Every session starts untracked: hooks record nothing until a session starts tracking (`cocheck track start|stop`, which the hook recognises by the command on a Pre and keys by the hook's own session id). `cocheck track start` refuses a home folder, a filesystem root or a folder that contains the home.

## Wiring: Claude Code

User-level, written by `node scripts/install.ts --home <dir> [--folder <dir>]` (see [install.md](install.md)); do not paste JSON by hand. The installer merges seven entries (PreToolUse, PostToolUse and PostToolUseFailure with matcher `*`; Stop, SubagentStop, UserPromptSubmit and SessionStart with no matcher) into `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR/settings.json`). `SessionStart` records nothing: it only sets the environment of the session's Bash calls for the attribution write hooks. Each command is built by the platform's hook command builder, and the `COCHECK_MANAGED=1` marker is how uninstall finds exactly CoCheck's entries. On a Mac it has this shape:

```
COCHECK_MANAGED=1 COCHECK_HOME='<home>' [COCHECK_NODE='<node>'] /bin/sh '<cocheck>/scripts/hook-launch.sh' '<cocheck>/dist/hook.js' --host claude
```

The launcher finds Node when the hook fires. Claude Code sets `CLAUDE_PROJECT_DIR`, so `--folder` is not needed.

**The registry.** `<COCHECK_HOME>/watched.json` (`{"version": 1, "folders": [absolute paths]}`, written by the installer) no longer switches recording on: the tracking gate does. The hook still reads it as extra scope for the attribution write guards. A registry that exists but cannot be read or parsed fails a tracked session's event with exit 1 and a failure marker, and a command carrying `COCHECK_MANAGED=1` whose home has no registry fails the same way. Paths are compared after resolving symlinks and `..`, and `/x/proj-evil` is not inside `/x/proj`.

Claude Code sends `session_id`, `cwd`, `hook_event_name`, `tool_name`, `tool_input` (Bash: `command`, `description`), `tool_response` (Post only) and `tool_use_id`.

## Wiring: Codex

The installer writes CoCheck's `[[hooks.X]]` entries into `$CODEX_HOME/config.toml` (default `~/.codex/config.toml`) for SessionStart, PreToolUse, PostToolUse, SubagentStart, SubagentStop, Stop and UserPromptSubmit, with `--host codex`. It refuses to change a file whose hooks are written inline, and says so. Codex sends no failure event (a failed call arrives as a Post), so there is no PostToolUseFailure entry. Codex asks the user to trust new hooks before they fire; the installer says so, and CoCheck records nothing from Codex until they are trusted. Codex sets no project-folder variable, so the hook takes the payload's absolute `cwd` as the task folder when `--folder` is not given and no folder was recorded by `cocheck track start`.

## Wiring: Copilot

The installer writes one file, `$COPILOT_HOME/hooks/cocheck.json` (default `~/.copilot/hooks/cocheck.json`), owned by CoCheck, with an entry for each of `userPromptSubmitted`, `preToolUse`, `postToolUse`, `postToolUseFailure`, `agentStop` and `subagentStop`; each command carries `--host copilot --event <name>`. The `preToolUse` entry always exits 0, because a non-zero exit there blocks the person's tool call. Like Codex, Copilot sends the task folder as the payload's `cwd`. Copilot also runs the hooks of a repo's `.claude/settings.json`; the Claude entry's run that Copilot started records nothing, and the Copilot entry does. Whether hooks in `~/.copilot/hooks` ask for trust is not verified.

## Adding a host

Each platform's sourced capabilities, hook events and recordings live in `platforms/` (see `platforms/README.md`); read the platform's folder there before writing its profile.

A new agent is usually a manifest and no code: see "Harnesses" below. The rest of this section is the profile a manifest compiles to, and the first-party code behind Codex and Copilot's extras.

Everything CoCheck knows about one host lives in one profile, behind the `HostProfile` interface in `src/hosts/types.ts`. Claude Code's is the manifest `harnesses/claude/cocheck-harness.json`; `codex.ts` and `copilot.ts` are modules under `src/hosts/` beside their manifests. The rest of the code asks the profile and never tests a host name.

A profile declares:

- `key`, `displayName`, `chip`, `testedVersions`: identity. The key is what `--host` takes and what ledger rows and journal records store.
- `eventKinds` and `capabilities`: how the host's hook event names map to CoCheck's kinds, and what the host lacks. `capabilities.failureEvent: false` (Codex) means a failed call arrives as a Post; `reportsFailureEvents` in `src/hosts/index.ts` reads it.
- `fields`: where each field sits in the payload (session, call id, tool name, tool input, session file path, last message, prompt), and `callReason`, the tool-input key that carries a per-call reason, if the host has one.
- `narration`: the ranked `sources` of a call's words, each with when it can be read (`pre` or `post`); `foldLine`, which folds one line of the host's session file into the narration cursor; and `closing`, the closing words the cursor holds at a Stop.
- `sessionFile`: whether the file is found from the session id alone, and `locate`, the host's own folder layout, used when the payload names no path.
- `coverage` (optional): `readCalls`, every call id the host's session file holds, for the coverage check at Stop.
- `install` (optional): the host flag written into the hook command, the folder variable the host sets or `folderFromPayloadCwd`, the config file, the events CoCheck installs, and `addHooks`, `removeHooks` and `missingEvents` for the edit of CoCheck's marked entries.
- `shape`: the fields each event is expected to carry. Not read yet.

Display names come from the profiles (`knownHostLabel`). Two host strings stay outside `src/hosts/` on purpose: `MAIN_LANE` in `src/timeline/attribution.ts`, the stored lane key that existing ledgers and pages carry, and the narrator's `claude` binary lookup.

## Harness manifest (v1)

A harness can be described by data alone: one `cocheck-harness.json` with `"schema": "cocheck-harness/1"`. The TypeScript type is `HarnessManifest` in `src/hosts/manifest.ts` (every field is documented there, and `validateManifest` names the field of any error, for example `toyagent/cocheck-harness.json: events.beforeTool: unknown kind "tool-pree"`). `compileManifest` (`src/hosts/compile.ts`) turns it into a `HostProfile`. A manifest holds no code: a payload path is `a.b` or `a[0].b`, a failure or refine rule is data, and behaviour that is not data is first-party code the manifest opts into by name (`"extras": [...]`, the table in `src/hosts/extras.ts`; an unknown name fails validation). A failure rule reads the failure's words from `text` (the first path holding text; with `nonEmpty`, a `tool-post` rule takes words there as the failure itself) and, when a `flags` path is `true` and `text` gave none, from `flaggedText` (a path, or `{ "path": ..., "blocks": true }` for a list of `{ "text" }` blocks joined by line breaks). A payload that keeps every field at a top-level key is read as it is. Claude Code ships this way (`harnesses/claude/`; its transcript readers are the extras `claude-transcript-narration`, `transcript-helpers`, `transcript-coverage`, `claude-reveal` and `claude-session-title`, in `src/hosts/claude.ts`). `callId` is `{ "payload": <path> }` (the host's id), `{ "synthesized": true }` (made up) or both together (the host's id when it sends one, else made up; Copilot). `install.notes` is a note printed after install (`{launcherDir}` and `{home}` are filled in). `install.editorExtra` names the first-party extra that supplies the config editor when the generic JSON editor does not fit (Codex's TOML editor, `codex-toml-editor`). `install.path` takes `{home}`, `{project}` (the task folder, for a workspace hook file), `{env:NAME}` and `{env:NAME|fallback}`, checked when the manifest loads. `install.entryTemplates` gives some events their own entry shape, falling back to `install.entryTemplate`. `install.skillRoot` is written with `/` and joined for the platform, so Windows gets `.claude\skills`. Every manifest pattern, built-in ones included, must pass the structural bound `patternProblem` (no lookaround, backreference or nested repetition), so a rule that needs "not this" is written as an earlier rule that keeps the kind, as Copilot's notification rule does.

The first-party extras each shipped host names (`extras` in its manifest):
- claude: `claude-transcript-narration`, `transcript-helpers`, `transcript-coverage`, `claude-reveal`, `claude-session-title`, `install-default`.
- codex: `codex-rollout-narration`, `codex-rollout-locate`, `codex-helper-rollout-lookup`, `codex-rollout-call-readers`, `codex-display-text`, `codex-session-title`, `codex-failure-read` (the failure read from the session file), `codex-tool-name` (the reported tool name's strip), `codex-trust-probe`.
- copilot: `copilot-events-narration`, `copilot-events-locate`, `helper-linker`, `copilot-session-title`.

Where manifests live: the ones that ship with CoCheck are under `harnesses/<key>/` at the repo root (data, copied to `dist/harnesses/` by the build, so they ship wherever `dist/` does). A person trying a new harness puts one at `<CoCheck data home>/harnesses/<key>/cocheck-harness.json` (`$COCHECK_HARNESS_DIR` replaces that folder, for tests); to ship it built in, add it to the first folder by a pull request. The folder name is the key, and a manifest may not reuse the key of a host that exists.

What a harness loaded from the person's folder may not do: its events never prove more than "inferred" (a change is still credited to that harness's call, never to "outside the agents"); it may not tag shell calls (`argvTag`); and `cocheck install --for <key>` prints the config path and the hook entries to add instead of editing the harness's config. A manifest that does not load is skipped with one line in `cocheck status` (and in `<data home>/harness-skipped.txt` from the hook); every other host keeps recording.

A harness that also runs other hosts' hooks (Cursor runs the hooks of `~/.claude/settings.json`) declares `capabilities.readsForeignHooks` and a `foreignHookFingerprint`, the payload shape of such a run. A built-in harness's fingerprint decides on shape alone: another host's hook that gets a matching payload records nothing, because the reading harness's own entry records it (Copilot). An outsider's fingerprint has the same effect only while the outsider's own CoCheck hook is installed for the payload's folder: its config file (the `install.path` with `{project}` set to the folder the payload names through `fields.cwd`) exists and carries CoCheck's hook for every event its install block lists, the same test `cocheck status` uses for "installed". Otherwise the payload is recorded as before, so a fingerprint can never make a run go unrecorded. The check reads that one config file, and only for a payload that already matched the fingerprint. `cocheck status` names each fingerprint in force, for example `Claude hook skips payloads from Cursor (its CoCheck hook is in <folder>/.cursor/hooks.json)`, looking in the install's folder and the watched folders.

The pass bar is `test/harness-toy.test.ts`: a toy harness with a payload shape unlike any built-in one, written only as a manifest plus recorded payloads, records a session end to end with no change under `src/`. The full public specification comes with the conformance kit.

## Harnesses

Every agent CoCheck reads is a harness: one data file, `cocheck-harness.json` (schema `cocheck-harness/1`), that says how the agent's hook payloads look. The full specification is `public-kit/harness/spec/v1.md`; the step-by-step guide is `public-kit/harness/GUIDE.md`. The manifest fields and their checks are described under "Harness manifest (v1)" above.

Where manifests live:

| Place | What is there | How CoCheck treats it |
| --- | --- | --- |
| `harnesses/<key>/` at the repo root | The built-in harnesses: `claude`, `codex`, `copilot`. The build copies the folder to `dist/harnesses/`. Their cases are in `public-kit/harness/cases/<key>/`. | Built in. May earn the stronger credit bases (`host-reported-edit`, `argv-tag`). `cocheck install` edits the agent's config. |
| `public-kit/harness/harnesses/<key>/` | Harnesses that are not built in: `cursor` and `antigravity`. Each has its manifest, its recording and its cases. | Not loaded by default. Copy the folder to `<data home>/harnesses/<key>/` to use it; it then loads as an outsider. |
| `<data home>/harnesses/<key>/` | A harness you are trying. `$COCHECK_HARNESS_DIR` replaces this folder. | Outsider. See "Trying a harness from your data home" below. |

What a manifest says, in short:

- **Events.** `events` maps each event name the agent sends to a kind (`prompt`, `tool-pre`, `tool-post`, `tool-failure`, `stop`, `subagent-stop`, and others). `eventFrom` says where the name is: a payload path, or the hook command's `--event` argument. A name mapped to `other` is carried and not acted on. `unverifiedEvents` lists events the agent documents that no recording shows; they are never mapped or installed.
- **Credit by inference for unlisted tools.** `toolClasses` says what each tool does. A tool not listed is unknown: CoCheck reads nothing from its input, but a change found in the folder while its call is open is still credited to that call, on the basis `inferred`. List a tool as `never-credited` (or `read`, `read-only`) to say it does not write.
- **`{project}` in `install.path`.** The task folder, for an agent whose hook file sits in the workspace, for example `{project}/.cursor/hooks.json`. `cocheck install` uses `--folder`, else the folder it runs from; `cocheck harness record` uses its scratch folder.
- **`install.envelope`.** Extra top-level keys for a config file CoCheck creates, for example `{ "version": 1 }`. A file that already exists keeps its own keys and gets none added. A harness in your own folder gets the same keys in the entries that install prints.
- **Per-event `entryTemplates`.** `install.entryTemplates` gives some events their own entry shape, for an agent whose config takes a group for some events and a plain handler for the rest. Every other event uses `install.entryTemplate`. Install, uninstall and the missing-hook check read each event in its own shape.
- **`failure["tool-post"].nonEmpty`.** For an agent whose Post carries an error field that is empty when the call worked: with `text` naming that field, the call failed when the field holds words.

### Trying a harness from your data home

1. Copy the folder that holds `cocheck-harness.json` to `<data home>/harnesses/<key>/`. The folder name is the key. A key that already exists is refused.
2. Run `cocheck install --for <key>`. For a harness in your own folder, install prints the config path and the hook entries to add, and does not edit the agent's config. Add them yourself.
3. Run the agent on a small task, then `cocheck open`. `cocheck status` shows the last event seen from each harness, and names any manifest that was skipped and why. The hook keeps the same list in `<data home>/harness-skipped.txt`.

An outsider's events never prove more than `inferred`, and it may not tag shell calls (`argvTag`). Its `foreignHookFingerprint` makes other agents' hooks skip a payload only while its own CoCheck hook is installed for that folder (see "Harnesses" above). A harness that works and has its cases can be shipped built in by a pull request: see "Add a harness by PR" in [CONTRIBUTING.md](../CONTRIBUTING.md).

## Limits

- Inherent, not fixed: a hand edit made while an agent call is running is credited to that call. Nothing in a hook payload tells the two apart.
- The hook diffs no file. Every file in the folder, whatever its type, is kept as states (hash, size and stored bytes); what changed inside a claimed file is the connector's answer, and the review server asks for it, not the hook (`src/hook-adapter.ts:48`, plan H1).
- During a call, nothing is known: a change is credited only when the next Pre, Post or expiry looks, to the calls open then that may have made it. Honest parallel calls therefore share each other's writes, and a hand edit made while any call is open is credited to those calls.
- A folder that is not an absolute path to an existing directory makes the CLI exit 1 with a message instead of scanning nothing (a folder with no workbook is not refused).
- Ghost call: a call whose Pre was seen but whose Post never comes (denied, interrupted, or a host that drops the event) stays open until Stop or 10 minutes, and shares every change found meanwhile. Its Stop-time op names only what other calls' sweeps gave it.
- Background jobs: after Stop or the 10-minute expiry, a job's writes look like changes from no agent call and show `unlogged`.
- Copies: a new file whose bytes exactly match a state already seen in the task is recorded as a copy, credited to the call open at the sweep that sees it (`copyOf`, `src/hook-adapter.ts:2212-2219`). The match is the SHA-256 of the bytes and nothing else. A near-copy (any byte different) is not a copy.

## Scoring a run

Every op records how its call closed in `closedBy`: `post`, `failure`, `stop` (the session's Stop closed it), `expiry` (10 minutes passed), `ghost-post` (a Post whose Pre was never seen), `late` (an op written for a call that had already closed, for a change a tagged write of it made later) or `refused` (a Codex call whose session file shows the host refused to run it). A failed call (the host's PostToolUseFailure event, or a PostToolUse whose `tool_response` has `is_error` or `isError` true) also carries the host's `error` text in the op, cut at 2,000 characters, and its ledger `result_code` is `TOOL_FAILED`, never `OK`. For a host whose session file records each call's exit status (Codex), a Post with no failure of its own whose call that file lists as failed becomes a failure marked inferred, matched by call id, never by text.

To list the calls that never got their own Post, after the run:

```
node scripts/hook-calls.ts "$COCHECK_HOME"          # calls closed by stop or expiry
node scripts/hook-calls.ts "$COCHECK_HOME" --all    # every call, with how it closed
```

One line per call: task, `tool_use_id`, `closedBy`, `background` or `foreground`, open and close times (UTC; `-` when unknown), how many other calls it is joint with, the intent, then the call runtime and the adapter overhead (`unknown` when a clock was missing, never 0); a final line gives the medians. A call closed by stop or expiry was open until then, so it shares every change found meanwhile. Treat its attribution as joint, not its own.

Joint figures are meaningless after a background start: a `run_in_background` call stays open until Stop or expiry, so every later sequential call is joint with it. Score only the calls before the first background start, or score the round as a whole.

## Timing

`node scripts/hook-timing.ts <workbook.xlsx> [calls] [decks] [transcript-mb]` runs the real CLI (one process per event) around edits of a temp copy of the workbook and prints median and max time per call (Pre plus Post). `decks` adds copies of a test deck to the task folder and `transcript-mb` gives every payload a transcript of that size to read for narration.

This figure is the whole hook process per call, from node start to exit, so it includes node start-up and is not the adapter's `processingMs`. In `scripts/hook-calls.ts`, "adapter overhead" is `processingMs` and "call runtime" is the wall time from Pre to Post, which is the tool call's own run and not overhead.

**Session coverage.** Each Stop reconciles its session and rewrites one `session_coverage` row: the journal's events, the ledger ops named by `session_id`, and the tool_use ids in the Claude transcript plus `<session>/subagents/agent-*.jsonl`, matched by `tool_use_id` only. Buckets keep a session from being complete: lost (an event with no done line, or a finished call event with no op), failed (a failure marker), host sent no event (a transcript call with no journal event; a denied call looks the same as a dead hook) and expired (a call whose last op says expiry closed it). Status is one of complete, lossy, not recorded, not checked. Complete needs the transcript read, every bucket zero and an intact journal. Claude transcripts are read; a Codex session is not checked. A degraded journal (`journal.degraded`) is lossy. A failed reconciliation overwrites the row with "not checked".

## Probing a host version

`node scripts/probe-host.ts <claude|codex|copilot> --out <dir>` runs one tiny scripted session on the host with hooks that log each event's raw stdin, and writes `<dir>/<host>-<version>/payloads.jsonl` (one `{event, ts, stdin}` line per hook call) plus `sessions/` with the session file(s). Use it after a host updates, to compare payload shapes with what the adapter expects. `--bin` and `--auth` (or `COCHECK_PROBE_BIN` and `COCHECK_PROBE_AUTH`) override the binary and the auth source.

The script writes only under `<dir>` and a scratch dir it removes at exit, and refuses a `<dir>` inside `~/.codex`, `~/.claude` or `~/.copilot`. The only read of the user's real config is the auth copy for Codex. SIGINT and SIGTERM remove the live scratch dir before the probe exits (SIGKILL cannot be caught), and at start the probe sweeps its own `cocheck-probe-XXXXXX` scratch dirs older than an hour.

Every file the probe writes to `<dir>` is scrubbed first: email addresses become `user@example.com`, and the home path (and its realpath) becomes `/Users/<user>`. If a token-shaped string (`sk-`, `ghp_`, `gho_`, JWT, `Bearer <value>`, a private-key header) is still there, the run fails and `<dir>/<host>-<version>/` is removed so no token stays on disk. The check is pattern-based, so a secret with another shape is not caught; read a recording before you commit it.
