# Timeline

The timeline is a read-only view of one task: its requests in the order they were sent, each split into runs, each run holding its calls. Each call has one plain line saying what the agent did, and, for every file the call is credited with, the before and after state hashes and the changes the format layer found between them. It is built by `src/timeline/` from ledger rows and never writes to the ledger.

## Routes

All four are GET on the review server, on localhost. They use the same token (`?t=`) and the same Host and Origin checks as the review page, and send no CORS headers.

`GET /timeline/<task>` returns the whole timeline as JSON under the schema id `cocheck.timeline/1`. A task that does not exist is a 404.

`GET /timeline/<task>/call/<id>/command` returns the raw command of one call, for an explicit expand. It is local only and is the only place the raw command appears. A call that ran no command is a 404; a task whose values have expired is a 410.

`GET /timeline/<task>/preview/<sha>` returns the stored bytes of one image file state (png, jpg, jpeg, gif, webp or svg), with the image content type of the file's own extension, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`, on every OS (nothing is rendered). The page loads it only through an img element, so an SVG never runs script. A state of a file that is not an image is a 404. The hash must be one of the task's own file states and its bytes must still be in the task's store, otherwise it is a 404. A state of a secret file is always a 404 and is never rendered or cached. Nothing in a URL is ever used as a path. Nothing in CoCheck draws a picture of a file a connector reads (Excel, Word, PowerPoint and any installed connector's types): such a file is never pictured by the core (`pictureTier` in `src/timeline/picture.ts`).

`GET /timeline/<task>/page` returns the general review page (HTML): one card per changed file, built from the timeline body alone (`src/timeline/page.ts`). Each change shows what happened, who (from `change.by`, see "Who made a change"), when, and why (the request text and the agent's own words, each labelled with its source), then what is different from the change's `generic` part, whose tier is `text` (hunks), `picture` (a labelled before and after pair with regions boxed, loaded from the preview route) or `fingerprint`. A format part shows folded below as location, before, after. A change with `generic.secret` (or whose name is a secret name) shows only the shared line "A secret file was changed: <relative path>" (`secretLine` in `src/secret-files.ts`, the same string as the hook record and the timeline label). A change with no `generic` part fails closed: its name, who, when and why, and nothing from inside the file (no format rows, no pictures). A picture whose width or height is not a positive number gets no boxes. The page response sends `Cache-Control: private, no-store`. The page has no script and no raw command; its CSP allows same-origin pictures only.

## ETag

The body carries an ETag built from the schema id, the highest op id, the highest state id, the values-expired stamp, the number of recorded state removals and the build. Send it back as `If-None-Match` and an unchanged timeline answers 304 with no body. The header is `Cache-Control: private, no-cache`.

## Where a line comes from

Every call line says where it came from. `agent-words` is a sentence from what the agent said around the call. `agent-description` is the short description the agent wrote on the call. `cocheck-translation` is CoCheck's own plain wording, with a basis: `tool-label` (built from the safe label fields recorded for a non-shell tool, such as a skill name, a file path, a search query for a built-in search tool, a URL's host, a helper agent's description), `tool` (from the tool name alone), or `shell` (from the first command word and the files a shell command names). CoCheck's own wording is never labelled as the agent's. A connector (MCP) call never has a query, name or title in its label, so its line names the tool and server and any file, never what it searched for. A shell call never builds its line from the label, and the label's `command` field is never read.

Anything the record does not hold is a sentence in a `missing` list, not an empty field.

## Privacy rules

The raw command is never in the timeline body. Paths inside the watched folder are shown relative to it (after `..` segments are resolved, so a path that climbs out of the folder reads as outside). A path outside the folder is cut to its file name; a path with a space in it, a Windows path (`C:\...`, `\\server\...`), and any link that is not plain http or https (`file:`, `sftp:`, `smb:` and the like) is cut whole. Plain http and https links stay as they are. A cut is marked `redacted` on the line.

Cached previews live in `tasks/<id>/previews` and hold values, so they follow the state they picture: they are deleted when the state is dropped (sign-off middle states, the size caps), and the whole folder goes at the 30-day value expiry and the 7-day idle expiry. After the 30-day expiry the timeline reads as expired and says so; it does not show a blank task.

## What changed in a file (`generic`)

Every file change in the timeline carries `generic`, whatever the file type. Any format part (`format`: the files layer's rows for a csv or text file, or one whole-file row; CoCheck reads no other format itself) stays where it is and never replaces `generic`. A file a connector reads has its change list in the change's `diff`, drawn from the connector's frozen document, and its `generic` is a fingerprint. The shape is shared by the text, picture and fingerprint tiers and is stated exactly:

```
generic = {
  tier: "text" | "picture" | "fingerprint",
  label: string,                      // plain words a page prints as is
  text?: { hunks: [{ beforeStart, beforeLines, afterStart, afterLines, lines: [{ op: " " | "-" | "+", text }] }], cut?: string },
  picture?: { before: sha | null, after: sha | null, width, height, regions: [{ x, y, w, h }], note?: string },
  fingerprint?: { before: { sha, size: number | null } | null, after: { sha, size: number | null } | null, kind: string, note: string },
  secret?: true
}
```

### Picture tier

A changed file that is not text, not secret and not read by a connector, that is a png, jpg, jpeg, gif, webp or svg image, is tier `picture` (any other type is a fingerprint). A state a connector reads (its row has a connector, a known connector claims its ending, or it shares bytes with such a state) is always a fingerprint with the reason "a connector reads this type of file, so CoCheck draws no picture of it" (`CLAIMED_NO_PICTURE`, `src/timeline/picture.ts:21`, checked first at `:266`). `picture.before` and `picture.after` are the state hashes, served by the preview route above (a created file has `before: null`, a deleted one `after: null`). `width` and `height` are the pixel size of the compared pictures (the larger of the two when they differ). `regions` are boxes around the pixels that differ between the two pictures, found by a pixel diff computed in CoCheck (`src/timeline/picture.ts`, a port of an earlier pixel-diff script, no dependency). At most 20 boxes are listed; past that they merge into one box around them all. A created or deleted file is compared with a blank page, so its content is the changed region.

The label is "The image as stored, drawn by your browser". Boxes exist only for a pair of PNGs. When the two stored states differ but no pixel differs by more than 2 of 255 in any colour, `note` and the label say "The change isn't visible in this preview". A picture is never given without that note when its regions are empty.

Two pictures count as the same when no pixel differs by more than 2 of 255 in any colour channel; smaller differences (anti-aliasing, font smoothing) are not changes. The memo of finished comparisons is keyed by home, task, the two hashes and the extension, so two homes never share an answer.

A secret file is never rendered and never pictured (names: `*.env`, `.env.*`, `*.pem`, `*.keystore`, `*.jks`, `*.token`, `service-account*.json`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `credentials*`, `secrets.*`, `.npmrc`, `.netrc`, `.pypirc`, matched on the file name at any depth, in `src/secret-files.ts`, applied by default): it is tier `fingerprint` with `secret: true` and the label "A secret file was changed: <relative path>". A file that is not an image, or a state no longer in the store, is tier `fingerprint`, with the reason in words in `fingerprint.note`.

Image previews are the stored bytes themselves, so they live and die with their state (there is no preview cache; leftover `tasks/<id>/previews` files from earlier versions are removed with their state). The pixel diff is bounded by picture size (pictures over 4 million pixels are not compared), not by how much changed.

### Text tier

The tier is chosen by content, never by extension. A changed file is tier `text` when the stored bytes of both its before and its after state decode as UTF-8 and the first 64 KB of each holds no NUL byte. A `.py`, `.json`, `.html`, `.svg`, `.ts`, an extensionless script and a CSV are all text. A NUL-bearing `.txt` is not: it is a fingerprint. UTF-16 and Latin-1 files are not text here either.

`generic.text` holds line hunks with 3 lines of context, aligned by the same line alignment the files layer uses, so an edited line is one `-` and one `+` and the label counts it once: "Text, 4 lines changed". A created file diffs against an empty file ("Text, new file, 12 lines") and a deleted one against an empty after ("Text, file deleted, 12 lines"). `beforeStart` and `afterStart` are 1-based line numbers; a side with no lines in the hunk uses the count of lines before it (so 0 for a created file).

Limits. When either side is over 2 MB the hunks are empty and `cut` says so in words. The 2,000-line cut counts aligned pairs (a deleted line paired with the line that replaced it is one), not lines: when more than 2,000 pairs changed, only the first 2,000 are listed and `cut` says how many. A file over 32 MB is read head-only (the first 64 KB, to tell text from binary), stays tier `text`, and its `cut` says its size in words. When only line endings, the final newline or a byte order mark differ, the hunks are empty and the label says no line changed.

### Order of tiers, and secret files

The loader tries the tiers in this order (`src/timeline/generic.ts`, `chooseGeneric`): text, then picture, then the fingerprint floor. Text is decided by content before the picture tier runs, so a text file never takes the picture path. A change with no entry in `TimelineInput.generics` is a fingerprint without bytes.

A secret file is checked before any tier. `LoadOptions.isSecret` defaults to `isSecretPath` (`src/secret-files.ts`): a base-name match at any depth on `*.env`, `.env.*`, `*.pem`, `*.keystore`, `*.jks`, `*.token`, `service-account*.json`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `credentials*`, `secrets.*`, `.npmrc`, `.netrc`, `.pypirc`. A secret file is tier `fingerprint` with `secret: true` and the label "A secret file was changed: <relative path>". Its stored bytes are never opened, no format layer reads it, its side sizes are `null` (unknown, never 0), and its format part carries hashes only. After the 30-day value expiry a secret change keeps `secret: true` and its line.

The fingerprint floor also catches a change whose side is not plain text and could not be pictured, and a change whose bytes are not available.

### Margin notes

Every change carries `note: { text, source: "rule" }`: one plain sentence built from rules in `src/timeline/notes.ts`, no model. Every row in `format.rows` carries its own `note` too; when a change has exactly one row, the change's note is that row's sentence. The ledger's own note on a change moved to `ledgerNote` (it was `note` before this).

The shapes with a rule (`src/timeline/notes.ts`): a file created (naming its folder, and what the connector says it holds), deleted, a text change (lines added, removed or edited), a picture file whose pictures were compared ("changed the picture <file>"), another file with a picture of both sides, a connector's re-save that changed nothing ("saved <file> again: nothing changed", or "nothing visible changed"), and a fingerprint change ("the file changed; CoCheck can't read inside it"). A change a connector listed reads from that change's own label and words: "<who> changed <label> from <before> to <after>", "added", "removed" or "moved" by its mark, or the label alone when a value is missing, over 60 characters or the task's values have expired. A file created and one deleted by one call with the same bytes get a literal sentence added ("Same content as <path>, which this call deleted."), never the words moved or renamed. Any other shape reads "<who> changed <where>". CoCheck itself writes no cell, formula, row or column sentence: for an Office file those words come from the Office connector's document.

The actor is `change.by.actor`, decided by `attributionOf` (see "Who made a change"): the host of the credited call ("Claude", "Codex"; "The agent" when neither the call nor the task names one), or the words for a change CoCheck can't credit to one agent. On a helper's lane the rail swaps it for "Helper n", and on the neutral lane for the names of the joint lanes. The place is the label the layer or connector gave, quoted exactly as written; a value over 60 characters is left out whole. A label over 48 characters, a bare cell address and the reader's "[object Object]" are not used as words.

Never a number or word the record lacks: every value and label in a note is the string the format layer already shows for that change, copied with no tidying ("25.00%" stays "25.00%", "3.10" stays "3.10"). Every digit run and every label or value in a note is a literal substring of the record. A value over 60 characters is left out whole, never cut. A secret file's note is exactly `A secret file was changed: <relative path>`. After the values expire a note names the place and no value or label. An outside path inside a value is cut to its file name like any other text in the body.

### Saved again, and files a connector reads

A connector's file is kept whole from the start. At the task's first event, every file a connector claims is copied whole, up to 2,000 files and 1 GiB together (`CLAIMED_ALLOWANCE_FILES`, `CLAIMED_ALLOWANCE_BYTES`, `src/hook-adapter.ts:512-517`). That allowance is separate from the general scan caps (500 files, 200 MB), which keep applying to every other file. Past the allowance a claimed file is kept as its hash with the reason in words, never a hard stop (`src/hook-adapter.ts:1751-1754`). A call that names such a file later copies it at its Pre. So a plain re-save of an Office file reaches its connector with both sides.

The nothing-changed rule. A connector that declares `"nothingChanged": true` in its `hello` says that an empty change list means it compared everything it can see. There is one signal for it: `vouchesNothingChanged` (`src/connector/nothing-changed-rule.ts:13-19`) is true only when the frozen document holds that declaration, lists no change and no picture, and carries no status, no "ask again", no pending or failed mark, no caveat, no issue and no `more`. Any issue refuses it, so a warning is never muted. The level is not read. The loader sets `DiffObject.nothing = "changed"` from it (`src/connector/diff-object.ts:60`), and the change gets `resave: true` only for a modified file that is not secret (`src/timeline/timeline.ts:1018`, field at `:191`). The note, the page line and the lane rule all read that one result. A failed, refused, timed-out, partial or pending answer never vouches.

What a re-save looks like. The note reads "<who> saved <file> again: nothing changed." (`src/timeline/notes.ts:118`). A re-save credited to one agent call stays on that agent's lane as a muted step with the side text "saved again, nothing changed" (`src/timeline/rail/model.ts:1349-1360`). A re-save credited to no single call gets no lane stop, is listed in the Files view as a muted version (`history`, `model.ts:127`, `:1360`), and is left out of the missing-credit sentences and the lane counts (`src/timeline/timeline.ts:1197-1198`).

Sign-off. The page's submit gate leaves out those history stops: a vouched re-save by no single agent is no open item, is not counted, and never asks to be looked at before sign-off (`src/timeline/rail/stop-status.ts:169-171`). For a file the hook's file-state chain tracks, the task store writes no changed-outside row, because the chain's own outside state is what the page shows and the sign-off gate reads (`src/tasks.ts:542-559`, `:592-593`).

What the built-in Office connectors vouch. Their readers do not list every kind of change (conditional formats, validations, presentation properties), so an empty list from them stands only when the two packages are byte-identical part by part, or differ only in the saved-file details an Office app rewrites on a plain re-save (allow-lists in `src/office/connector/shared/package-media.ts:620-640`). Only the per-save property fields are set aside (`dcterms:modified`, `cp:lastModifiedBy`, `cp:revision`, and the app fields Application, AppVersion, TotalTime, TitlesOfParts, HeadingPairs, `src/office/connector/shared/docprops-noise.ts:5-6`); a changed title, author, subject, keywords, Company or Manager is a real change. Any other difference becomes one `described` change in the connector's own words, never "nothing changed" (`src/office/connector/nothing-changed.ts`). A created or deleted file is never "saved again".

## Nothing is hidden

CoCheck states what it observed and never judges a file. It can say two things about a moment, each from one source.

(A) "The call that wrote <file> failed (<why>)." This comes only from the hook record's failure event, and only when every call credited with the change failed. The record holds no error text or exit code today, so the parenthesis says the host reported a failure and recorded neither.

(B) "CoCheck could not open the <before/after> version of <file> (<the reader's reason in plain words>)." This comes only from a failure of the same reader that draws that file's view, on those exact stored bytes (`readState` in `src/timeline/broken.ts`: the pdf.js reader, for `.pdf` only). CoCheck reads no Office file, so an Office file never gets a B line, locked or not; the Office connector says in its own document when it cannot open a state.

When both hold for one change, the moment reads as one sentence: "The call that wrote <file> failed, and CoCheck could not open the file it left." The words broken, damaged, corrupt, invalid and half-written never appear on the page.

1. The note and the view come from one read result: a state is noted as unopenable if and only if its view names that side as one CoCheck could not open (the sentence in the view's caveats). `Generic.unopened` holds the noted sides; the renderer calls the same reader on the same bytes.
2. A file kind with no CoCheck reader (text included: a side that is not text says so in other words), a reader that was not run, a reader that timed out and a reader that is unavailable produce no B line. Timeout and unavailable keep their wording about CoCheck. A state over the view's read cap (`OPEN_CAP_BYTES`) is not claimed about either.
3. Locked (an OLE header, `/Encrypt`) is a reason inside B, never a separate claim.
4. The check never throws, never rejects or stalls `loadTimelineInput`, and stays inside the existing read cap and concurrency. Any exception reading a state produces no claim plus one line in the view's caveats (`Generic.readerCaveats`).

B is appended to the change's event sentence ("Claude created x.pdf. CoCheck could not open the after version of x.pdf (...)"), never put in its place. A uses the change's own verb (created, deleted, changed).

A changed file with one side CoCheck cannot open draws the readable side in full (`readableSideOnly`) and names the other. When both sides fail, the card names both.

The failure this must never show is held in tests: a judgment word anywhere on the page, B on a state the format's reader opens, B on a kind with no reader, A on a call that succeeded or whose end was not reported, and a load that fails because of this check.

## Renderers and the view route

A renderer draws one change of one file as a `View`: the before and after of the thing that changed, with boxes round exactly what changed. The contract lives in `src/timeline/render/types.ts`; the registry in `src/timeline/render/registry.ts`. No network, no new dependency.

### Contract

```
FormatRenderer = { name: string, extensions: string[], view(before: Buffer | null, after: Buffer | null, change: ChangeInfo) -> View | Promise<View> }
ChangeInfo = { id: string, file: string, kind: "created" | "modified" | "deleted", generic?: GenericPart }   // what the timeline body holds for the change

View = {
  change: string,                         // the change key (Change.id)
  file: string,
  engine: string,                         // who drew it, named on screen: "drawn by macOS PDFKit" | "drawn by CoCheck from the lines of the file" | "macOS Quick Look, first page only"
  kind: "grid" | "pages" | "card",
  before: Pane[], after: Pane[],          // one pane per sheet (grid) or per picture (pages); empty for a card
  boxes: Box[],
  caveats: string[]                       // plain sentences; never empty when anything is hidden, unread or unsure
}
Pane = { id: string, label: string,
         grid?: { sheet, state: "visible" | "hidden" | "veryHidden", columns: [{ name, width, hidden }], rows: [ { gap: true } | { row, hidden, cells: { [col]: Cell } } ], merges: string[], moreRows: number },
         text?: { lines: [ { n: number, text: string } | { gap: true } ] }
         picture?: { sha: string, width, height } }
Cell = { ref, text, value: string | number | boolean | null, formula: string | null, numFmt: string, unformatted?: true, fill: string | null, bold: boolean }   // unformatted: text is the stored value because the number format could not be drawn exactly
Box = { side: "before" | "after", pane: string, cell?: string, line?: number, rect?: { x, y, w, h }, change: string, confidence: "exact" | "text-match" | "pixel" | "none" }
```

Rules. Boxes come from the data change; a pixel diff is only a cross-check. Confidence `exact` is a box from a line comparison (the text renderer); `pixel` is a box from a picture diff; `none` never carries a box: it is an honest card with a caveat. A box is never placed on a line that did not change. The picture and the data disagreeing is said in a caveat: data changed but the picture did not, or the picture changed but the data did not ("the picture moved and we can't say why").

Registry. Keyed by lower-case extension. `rendererFor(file, generic?)` returns the registered renderer; with no entry for the extension, a change whose generic tier is `text` (decided by content) gets the text renderer, else the fallback. Registered today: pdf, when the macOS page drawer was built (below). A state a connector reads (the Excel, Word and PowerPoint built-ins and any installed connector, by ending or by shared bytes) gets the claimed card whatever else is registered: kind `card`, no pane, and the sentence "A connector reads this type of file, so CoCheck draws no view of it" (`src/timeline/render/claimed.ts`, `src/connector/registry.ts`). The page draws that file from the connector's document instead. The fallback wraps the Quick Look picture tier as kind `pages`, confidence `pixel`, engine "macOS Quick Look, first page only"; with no picture it is kind `card`. No core renderer makes a `grid` pane (the `grid` shape stays in the contract because `view-v1.ts` and connector pictures use it).

### Route

`GET /timeline/<task>/view/<change key>` returns the `View` as JSON (`cache-control: private, no-store`). Same token, Host and Origin checks as every timeline route. A change key that is not one of the task's changes is a 404; a task whose values expired is a 410; a secret file (by name, or by bytes) is always a 404 and its bytes are never opened. The two hashes come from the change, never from the URL; a URL part is never a path. A state whose bytes are no longer stored gives a card whose caveat says so.

### Number formats (no longer drawn)

CoCheck's core does not format cell values, and the review page shows no cell grid. The Excel reader lives with the Excel connector (`src/office/connector/xlsx/`, `src/office/connector/excel/`), and so do the number-format rules (`src/office/connector/xlsx/numfmt.ts`). The connector uses only `builtinCode` from them, to name a built-in format id (`src/office/connector/excel/workbook.ts:10`, `:132`; `src/office/connector/xlsx/reader.ts:137`). The code that applied a format to a value is `test/helpers/xlsx-shown.ts`, a test helper that keeps the rules pinned and that no `src/` module reads (its header says so, `:4-6`).

The pinned rules refuse to guess: a code they cannot render exactly shows the stored value, marked unformatted. The Excel behaviours that differ from LibreOffice were checked against real Microsoft Excel for Mac 16.113.4 (`test/fixtures/numfmt/excel-real.json`); the 112-code oracle in `test/fixtures/numfmt/` is a frozen export of LibreOffice's "save cell content as shown", and its expected text never comes from CoCheck's formatter.

### PDF renderer

`src/timeline/render/pdf.ts`, engine label "drawn by macOS PDFKit", registered for `.pdf` only when the page drawer exists (`rendererFor` checks `dist/helpers/pdfpages`, or the path in `COCHECK_PDF_HELPER`, on each call). Without it, PDFs get the fallback like any other file type and nothing fails.

Reading and drawing are two parts. Every page's size and text runs come from the pdf.js reader, the same on every OS (`public-kit/helpers/pdf-text.mjs`, run by `src/timeline/render/pdf-helper.ts`; pdf.js ships in `dist/vendor/pdfjs`): one warm Node child process per CoCheck process, the bytes over a pipe, a 30 second limit per read that kills it, a 1 GB heap cap and an empty environment. The OS only draws pages to pixels (`public-kit/helpers/pdf.mjs`): on macOS `native/pdfpages.swift`, built with the system `swiftc` by `scripts/build-helpers.mjs` (the last-but-one step of `npm run build`) into `dist/helpers/pdfpages`, run as `pdfpages <pdf> --png <n> <out>` on a temp copy of the stored bytes with a 30 second timeout and SIGKILL; a missing swiftc, a non-macOS machine or a failed compile prints a warning and exits 0. Pixels are 2x the page's displayed size in points, origin top-left, page rotation and crop box applied.

Pairing and boxes. The text lines of the whole document, in reading order, are one sequence per side; the two sequences are aligned with `alignSequences` (the file layer's longest-common-subsequence pass, `src/formats/files/align.ts`), whitespace-insensitive. A line with no identical partner is changed: a line only on the after side is boxed on the after side (inserted), only on the before side on the before side (removed), a replaced line on both. Pages are never paired: an inserted paragraph that pushes every later line onto later pages boxes only its own lines. A changed number is a changed line and is boxed. Every box has confidence `text-match` and a `rect` in picture pixels. Which pages get a pane (`before:page<n>` / `after:page<n>`) is decided by the page statuses defined under "Pages are also compared by pixels" below: pages with boxes, changed pages, and pages with no partner are shown; identical pages are counted, not drawn.

Page pictures. A pane's `picture` is `{ sha, width, height, page }`: the state's hash, the page's pixel size and its 1-based page number. The browser loads it from `GET /timeline/<task>/pdfpage/<sha>/<page>?t=<token>` (image/png, `cache-control: private, no-store`). Same token, Host and Origin checks as every timeline route; the hash must be one of the task's own file states whose every recorded name ends in `.pdf`; a secret-named file (by name or by bytes) is a 404; the state's bytes must still be in the store (else 404); a page outside the document is a 404. Nothing in the URL is a path. The picture is drawn on request from a temp copy and is not cached, so no picture outlives the stored state.

A card, not a guess: a PDF the reader cannot read or open (damaged, locked, too slow), a side missing from the store, or a changed file in which no page differs in text or in pixels (below). The card carries a caveat saying which.

Accepted gaps: no lazy rendering and no cap on pages with boxes (a pane is made for each, and each picture is one helper run; only picture-only and page-break-moved pages are capped, at 20 per view); no content-hash cache of pictures; no pixel-determinism test (a pixel comparison of pages with matching text is added below). Granularity is a line: a changed number boxes its whole line, not the digits. A paragraph that re-wraps because of an edit shows as changed lines. Reading order across columns is the PDF's own content order, as pdf.js reads it. Tables, forms and annotations are read only as far as pdf.js reads them as text. Text runs are trusted only when pdf.js's pages are the pages the OS draws (count, and sizes within 2 px); otherwise the view is pictures only.


### pages are also compared by pixels (PDF)

Definition of "identical" (one rule everywhere). Two pictures are identical when no pixel differs by more than 2 (of 255) in any colour channel (`IDENTICAL_TOL` in `src/timeline/picture.ts`, the default of `diffPixels`). P=, the "match" card and its wording, and the image-file diff's "The change isn't visible in this preview" note all mean exactly that, and the on-screen words state the number ("no pixel differs by more than 2 of 255 in any colour"); nothing says "pixel for pixel". A page or image with a 5% gray fill added (about 13 of 255), or a single pixel changed by 3 or more in one channel, is never identical. Boxes are drawn at the same tolerance, so a pair that is not identical always has at least one box (a changed pixel makes a box of at least 1x1 pixel); there is no second, higher tolerance and so no page that differs yet shows with zero boxes. Rendering noise: no tolerance is needed for renders of one PDF page by the PDFKit helper, which are deterministic: two renders of the same page decode to byte-identical pixels (difference 0 at tolerance 0; test "render twice", macOS only). What is not covered: Quick Look previews of a file saved twice are not shown to be pixel-stable; a difference they introduce above 2 shows as a change.

Definition first. In a pages view (PDF) every page of the before side and every page of the after side gets exactly one status, from one function (`accountPages`, `src/timeline/render/pixel-pages.ts`; `accountDocument` in `pdf.ts` feeds it). A page can never be absent from the account, and a pane is built from the status map, not from "pages that hold a box".

- **T** - holds a text-match box. Shown, with its text boxes. Never compared by pixels and never given a pixel box. No cap.
- **P=** - paired 1:1 with a page on the other side and pixel-identical. The pairing is by identical page text, by position for text-less pages when both sides have the same page count, or by identical picture for text-less pages. Hidden, but counted: the view says how many such pages each side has and which.
- **P≠** - paired 1:1 and the pixels differ. Shown, with `pixel` boxes over the differing regions on both sides. No cap.
- **R** - has text, holds no box, and has no 1:1 partner because page breaks moved (a paragraph was inserted or removed and the lines reflowed, pages were split or merged, or its identical-text partner holds a box). Shown with no box, labelled "same text, page breaks moved"; its picture is not compared, and the caveat says so in plain words (nobody looked at those pictures, so a change to a picture, chart or fill on such a page could be there and would not show). A caveat names its before/after page group: the before and after pages joined by unchanged lines that go from one to the other, taken as connected components. The groups are for wording only; they never decide visibility.
- **U** - no text and no partner (an added or removed picture-only page). Shown whole-boxed by pixels.
- **S** - could not be drawn (or its partner could not). Named by page number in a caveat, never counted as matching.

Rules. Every page that is not P= is shown or named by number. Only U and R count toward a cap of 20 shown per view, and U pages (added or removed, no text) take the slots before R pages (page breaks moved); the rest are named as page ranges with a count. T and P≠ have no cap. A text pair keeps its 1:1 partnership only when neither page is T: if exactly one side holds a box, the other side is R, never dropped. A partner must also keep page order (the pairs outside the longest in-order run are treated as moved: text pages become R, text-less pages U). "Match" wording appears only when every page on both sides is P= (no S); the card stays only for that, for identical bytes, or, when nothing can be shown, for a document whose remaining pages could not be drawn (the card then says so and does not say the pages match). Page numbers in caveats come from one helper (`pageRanges`: `[1,2,3,5]` is "pages 1-3 and 5"; one page is "page 4") with singular and plural verbs. The view gives a count of the identical pages that are hidden, per side, rather than saying "Only pages with a box are shown".

Pairing (`src/timeline/render/pixel-pages.ts`, `pairPages`). Each page gets a signature, its lines whitespace-normalised and joined. The two signature sequences go through `alignSequences`; the pages it leaves out as identical pair in order, so a page pairs only with a page of the same text. A page with changed text has no partner (it is already boxed by text). A page that only reflows because an earlier paragraph grew has different text and no partner: it is shown as page breaks moved (status R), not compared, and never as a pixel change. Pages with no text pair by position only when both sides have the same page count. Text-less pages left over (counts differ, or the partner at that position has text) are drawn and matched by exact picture content in order (`matchByPicture`); a left-over page with no identical picture on the other side is added or removed. A pair is dropped when either page holds a text-match box; the page on the other side is then R.

Comparison. `comparePages` draws both pages as PNGs (the PDFKit helper, `renderPdfPage`; the tests inject their own), decodes them and runs the picture tier's differ (`diffPixels` at `IDENTICAL_TOL` = 2 per colour channel, then `regionsOf`, at most 20 boxes). The box rects are in the pictures' pixels and the same regions are placed on both sides. A picture that cannot be drawn or decoded is counted as skipped and said in a caveat; it is never reported as changed.

Caveat. The view says which boxes came from pixels: "Boxes on page N come from comparing the two page pictures pixel by pixel, not from text". The card for same-text files now says the page pictures match too.

Added and removed pages. Every added or removed text-less page (U) is shown on its own side with one whole-page box (confidence `pixel`) and a caveat naming it as added or removed; U and R pages together are capped at 20 shown per view and the rest are named as page ranges with a count. Pages with text that were added or removed are shown through their text-match boxes. The card says the pictures match only when every page on both sides is P=; a text page that merely reflows is R and shown, never summarised away. Declared limits (R pages are not compared by pixels, so a picture changed under reflowed text shows only as page breaks moved; pairs are 1:1 by order, so a moved page reads as R or U rather than as moved; a card for a document with only undrawable pages says so and carries no pane). A changed text-less page in a deck of unequal page count reads as one removed plus one added page (exact picture match, no tolerance). Cost is one helper run per compared page per side, with no cache.

### the task folder, text files, created and deleted files

The task folder. A hook-adapter task's folder is always the tail of its client name: the write side records the `--folder` as the marker `dir` (never the directory of the first accepted file, which may be outside it, e.g. an agent's temp folder), and the read side ignores any marker `dir` for a hook task, so runs recorded by earlier versions read correctly too. The client name is `<host>-hook:<folder>` (e.g. `claude-hook:/Users/user/Desktop/cocheck-run/work`). `taskFolderOf` in `src/timeline/load.ts` is the one place that reads it: for a hook task the client name; for any other task the marker's `dir`, else the client name; with the `<host>-hook:` prefix stripped, trailing slashes removed, and null unless the result is an absolute path. Every inside/outside test (the `outside` flag, relative file names, the folder tree) reads that value.

Text renderer (`src/timeline/render/text.ts`, engine "drawn by CoCheck from the lines of the file"). Chosen for any file the text tier read, whatever its name. `Pane.text = { lines: [ { n, text } | { gap: true } ] }`: numbered lines (1-based, the file's own numbers), cropped to the changed lines plus or minus two with a `gap` marker between far-apart bands and after the last band when lines follow. A `Box` on a text pane has `line` (the 1-based line number in that pane), `pane` `before:text` or `after:text`, confidence `exact`. Lines are aligned with the same pass the text tier uses (`alignSequences`); a line with no identical partner is changed and boxed (removed lines on the before side, added on the after side, a replaced line on both). An unchanged line never carries a box. A side with no changed line (a pure insertion or removal) has no pane. Kind is `pages`. A card, with a caveat: a change in line endings, final newline or byte order mark only; a file over the text tier's size limit; not plain text; a side missing from the store. Lines are cut at 1000 characters and a pane at 400 drawn lines, both said in a caveat; a CSV is drawn as lines, not a grid.

Created and deleted files. A created file draws its After side and a Before pane `{ id: "before:empty", label: "There was nothing here yet" }` with no `grid`, `text` or `picture`; a deleted file draws its Before side and an After pane `{ id: "after:empty", label: "There is nothing here now, the file was deleted" }`. No boxes. Text: the first 40 lines, then a gap marker and a caveat when more follow. A missing state stays a card.

## Subagent lanes

Definition. A lane is one line on the railroad. The main line is Claude's; each subagent (helper) gets its own numbered lane that branches off Claude's line and merges back into it, as on the review page. A helper is identified by the `agent_id` its hook payloads carry, and by nothing else. A call with no agent id is on the main line; it is never moved to a helper's lane, and no timing, name or order is used to guess an agent.

Probe finding (read-only; event kinds and field names only, never content). Source: the Claude Code 2.1.296 binary's hook input schema, the session transcript's field names, and this repo's adapter and fixtures. No captured live hook payload exists in the repo or in the recorded hook state (`state.json` holds no payloads), so the finding below is the schema the host declares, not a recorded payload. Unverified until a live hook is logged.
- Every hook's base input carries `agent_id` and `agent_type`. The schema says `agent_id` is "present only when the hook fires from within a subagent ... absent for the main thread, even in --agent sessions", and `agent_type` is the agent's type name ("general-purpose"); it can also be present on the main thread of a session started as an agent, which is why only `agent_id` decides the lane. So PreToolUse, PostToolUse and PostToolUseFailure of a call made inside a subagent carry both.
- `session_id` is the parent session's. Nothing links an agent id to the call that launched it (`SubagentStart` has `agent_id` and `agent_type`; `SubagentStop` has `agent_id`, `agent_type`, `agent_transcript_path` and `last_assistant_message`; neither has the launching call's `tool_use_id`).
- Session transcript: subagent lines live in `<session>/subagents/agent-<id>.jsonl` with `isSidechain: true` and `agentId`, and a `.meta.json` with `agentType`, `toolUseId` (the launching call), `spawnDepth`. The adapter does not read them.
- Codex: not probed. A Codex payload with no `agent_id` stays on the main line.

Record. A call op carries `agent_id` and `agent_type` (args), written only when the payload had a valid `agent_id` (a plain string of at most 128 characters from `A-Za-z0-9_.:-`); `agent_type` is kept only with it. Forward-only: ops written before this item have neither and read as the main line.

Timeline body. Each call has `agent: { id, type } | null` (`type` may be null). `null` is the main line.

Placement. Definition: an agent's calls belong to the request of the main-stream call that launched it. The launcher is exact, not inferred. Claude Code writes `<transcript dir>/<session_id>/subagents/agent-<agent_id>.meta.json` beside the session transcript. When a call carries `agent_id`, the hook adapter derives that path from the payload's `transcript_path` and `session_id`, reads the file (regular file only, at most 16 KB), takes the one field `toolUseId` (kept only as a plain id string) and records it as `launch_tool_use_id` on the call op. It never reads the agent's `.jsonl`. Any problem (no path, no file, a link, too large, bad JSON, bad id) leaves the op unchanged, and the read costs one small file per agent call.

A lane's owner is the request that owns the call named by the lane's launch id (the first call of the lane that carries one; the launcher must be in the same session and not a call of the same agent). If that launcher is itself an agent's call (a helper started by a helper), the owner is the request of its own owner. With no launcher recorded, or one the record does not hold, the lane falls back to its first call's request. This holds on both placement paths: by start stamp, and the time/step fallback used when any call lacks `startSeq`, where each lane remembers the request group it was placed in and its later calls go there instead of following the moving pointer. The same agent id in two sessions is two agents. A call with no agent id is placed by its own start and a launch id on it is ignored.

Residual gap: a lane with no readable meta file (a host that does not write it, a deleted file, a payload with no `transcript_path`, ops written before this rule) is placed by its first call, so a helper whose first call came after a later request was sent is credited to that later request. On the fallback path a launcher in a different turn than the agent's call is not seen, and the lane follows its first call there. The meta file layout is read from one on-disk example (field names only), not from a documented contract.

Runs. A run never mixes lanes: the main line and each agent are cut into runs separately, and a request's runs are listed in the order their first calls started.

Rail. Helpers are numbered from 1 in the order they first appear among the moments (`agent:<n>`, chip `<n>`, "Helper <n>"). A helper's line branches off Claude's last moment before its first one and merges into Claude's next moment after its last one; with no earlier Claude moment it starts on its own, with no later one it ends without merging. A helper's moments name the request that owns it (placement above), and its moment heads name its type. A helper's margin notes (the moment note and its row notes) start with the lane's name, "Helper <n>" (the chip's number), instead of the host's; main-line notes keep the host. Only a helper that changed a file has a lane: the rail draws moments, and a helper that only read has none.

Accepted gaps: no Codex probe; no per-lane legend toggles of its own (the legend lists every lane and the existing hide/show works on helper lanes, untested); no firstStep carry-over. Also: an agent's calls are not narrated (the narration reader skips sidechain lines by design, so they read "no narration recorded"); the wake of a background helper is a merge stop and a nested helper branches off and merges into its parent helper's lane (below); a helper with no readable launcher meta is placed by its first call (see Placement).

## Request stops

Definition. On the review page a request stop's main area is the request text, verbatim from the record, as the central element. A request stop has no Before/After panes, no tape-deck view fetch and no side card repeating the text. The model gives the stop `request: { text }` (a request's texts joined by a blank line) and no `card`; the page hides the stage and shows `#reqview`/`#reqtext` instead. The heading counts requests from 1 in the order shown ("You made request 1"), whatever index the record carries (it can start at 0).

Rules. The text reaches the page only through `textContent` (the area is `white-space: pre-wrap`, so line breaks are kept; long text wraps with `overflow-wrap: anywhere`; there is no clamp and no "show all"). Every render flips the request area and the stage first and clears the panes, tabs, trees, notes, leaders and caveats on a request stop, and clears the request text on every other stop, so stepping request -> change -> request -> change leaves nothing of the previous stop.

Tests. The request-stop test builds the model with the real builder and runs the real `review.js` and `view-table.js` in a vm with a DOM stub, stepping with the page's own arrow-key handler; a request holding `<script>` and `<img onerror>` renders as literal text with no element built from it. The stub is not a browser, so layout (wrapping, the look) is for a real-use check.

Wakes from background agents are not requests (below). The start stop keeps its card.
### what a note says CoCheck knows

One rule for every note and caveat: "can't read inside it" appears only when CoCheck has neither a format reading nor a picture of both sides of the file. Never a claim of a picture or a reading it lacks.

- A picture file (png, jpg, jpeg, gif, heic, tiff, bmp, webp) whose picture tier holds both sides is a picture change: "Claude changed the picture <file>". Its view carries the caveat "The pink boxes mark where the pixels differ, found by comparing the two pictures, not by reading them." (only when there are boxes; the boxes are confidence `pixel`). The "first page or sheet only" caveat is left off picture files.
- Any other file with a picture of both sides: "Claude changed <file> (CoCheck has a picture of both versions, not a reading of the file)"; the pixel-box caveat is added to its view too.
- A PDF whose renderer is available on this machine: "Claude changed <file>" with no reading claim and no "picture of both versions" wording; the view (pages, boxes, caveats) carries what changed. Where the renderer is unavailable, the picture wording above applies.
- A file a connector reads (Excel, Word, PowerPoint, or an installed connector's types): never the picture wording, because CoCheck draws no picture of it. The note is the connector's own: its changes in its words ("Claude changed <label> from <before> to <after>"), or "Claude saved <file> again: nothing changed." when its document vouches that (see "Saved again" above), or the fingerprint wording below when the connector gave no document.
- Everything else (fingerprint tier, one side missing, no format reading) keeps "the file changed; CoCheck can't read inside it".

Declared limits: a PDF whose text a renderer read with no difference gets no "text did not change" note, because notes are built from the record (format layer and picture tier) and the renderer's text comparison happens only when the view is opened. Such a file reads as the "picture of both versions" note when it has pictures. The Quick Look engine name on a picture file is "macOS Quick Look" (a picture has one page); documents keep "first page only".
## Subagent lanes for older runs

Definition. At read time, a call op with no `agent_id` is matched by its `tool_use_id` against the tool_use ids in its own session's subagent transcripts. A match gives the op that agent's lane, placed by the subagent-lane rule: the request owning the launching call (the agent's `.meta.json` `toolUseId`), else the lane head. This brings back the lanes of runs recorded before CoCheck began stamping `agent_id` on call ops (forward-only).

Where it reads. `<transcripts root>/<task folder with every character outside A-Za-z0-9 turned into "-">/<session_id>/subagents/agent-<id>.jsonl` and `agent-<id>.meta.json`. The root is `$CLAUDE_CONFIG_DIR/projects`, else `~/.claude/projects` (the review server takes an override for tests). If the task folder has no directory for the session, any project folder under the root that holds `<session_id>/subagents` is used (the session id decides, at most 2000 project folders looked through). Only the op's own session is ever read.

What it reads. From a transcript, only the `id` of each `tool_use` block in an assistant message, kept only as a plain id; from the meta file, only `toolUseId` (the existing reader). Transcripts are read in 1 MB chunks, line by line; a line is parsed only when it mentions `tool_use`, and nothing from it but ids is kept. A line that does not parse, is over 8 MB, or names another session gives no ids.

Refusals (what the rule must never do). A stamped `agent_id` (any non-null value) always wins and the op is left as stored. An op no transcript names stays on the main line. An id that two agents' transcripts both hold matches neither. A transcript of another session never claims an op. A missing or unreadable folder, a link anywhere between the root and the file (project folder, session folder, `subagents` folder, or the file itself: each is checked with `lstat`, and files are opened with `O_NOFOLLOW`), a file over 64 MB, or more than 200 agent files or 256 MB read for one session, changes nothing for the files it skips. An agent id (from a file name) or launcher that is not a plain id (up to 128 of `A-Za-z0-9_.:-`, never starting with `.`) is not used. `cleanId` now rejects `.`, `..` and leading dots everywhere it is used, which also applies to the hook adapter's `agent_id`, `agent_type` and `session_id`.

Stored ops are never rewritten. The backfill stamps an in-memory copy of the rows (`loadRows`), so the ETag follows it and the ledger is only read. Ids per transcript are cached by path, size and modified time (256 files), so polling re-reads nothing that has not grown.

Declared limits. A backfilled op carries the agent id and launcher but no agent type (the lane reads "Helper n" with no type): only `toolUseId` is read from the meta file. A transcript that was deleted, or a session whose folder is not under the root (another machine, another config dir), leaves the run as stored. A call whose tool_use id is not in any agent transcript (the agent never wrote it, or the line was dropped) stays on the main line. A transcript over 64 MB gives no lanes. The transcripts root itself may be a link (it is the configured location); a folder swapped for a link between the check and the read is not caught. Tests run on synthetic transcripts only (and the test bootstrap replaces a `CLAUDE_CONFIG_DIR` that is the real `~/.claude` with a temp dir); a real run is checked separately.

## Background agent wakes

Decision: a finished agent has its own lane, and its railroad merges back into whoever or whatever spawned it.

Structure (defined first; the rules below rest on it). A wake prompt is parsed as a sequence of top-level blocks (`parseBlocks` in `src/timeline/runs.ts`).
- A block starts with `<task-notification>` at the start of the prompt, or right after the previous block's closing `</task-notification>` (whitespace allowed between). Nothing else starts a block. Anything inside a block, `<result>` and `<usage>` included, can never start a block and is never read as a wake field.
- A block's own top level (its head) is everything from its opening tag up to the first `<result>`, `<usage>` or `</task-notification>`. The fields (`<tool-use-id>`, `<status>`, `<summary>`) are read from the head only. A block with no plain `<tool-use-id>` in its head is not a wake (the host writes the fields before the result; a result placed first leaves no head id, which is the safe direction).
- If the head ended at `<result>` or `<usage>`, the rest of the block is an opaque span. In it, each `<task-notification>` counts up, and each `</task-notification>` that comes right after a `</result>` or `</usage>` (whitespace allowed) counts down, or, when the count is 0, closes the block. A closing tag after anything else is content and counts for nothing. This is the chosen way to resolve a quoted notification (a `<result>` holding a whole well-formed notification balances and the outer block ends at its own closing tag) and a lone closing tag in prose (ignored). If the span never balances (a lone opening tag, a missing closing tag), the block runs to the end of the prompt: nothing after its first `<result>` opens a block, so a malformed block can lose a later wake or the text after it, never invent one. Not chosen: matching `</result>` pairs, because a result may itself quote `</result>`, which a depth count of notification tags absorbs.
- Text outside the blocks. If the prompt has non-whitespace text after its last block, that text (trimmed) is a request of its own, shown as "Your request" with only that text, under the same submit stamp; the block text is never shown. With no such text there is no request. A prompt that starts with a block but has no valid block is a request with its whole text, as before.

Definition. A wake is a prompt whose text starts with `<task-notification>` and whose `<tool-use-id>` names a launcher call recorded in the same session. A launcher call is a call of the tool `Agent` or `Task`, or any call that an agent's calls name as their launcher (`launch_tool_use_id`). Anything else stays a request, unchanged: a typed prompt that starts with, or only contains, `<task-notification>` and names no launcher call in its own session (no id, an id the record does not hold, a call of another session, a call that is not a launcher) is shown as the request it is, with its text. The host's notification carries `<task-id>`, `<tool-use-id>` (the launching call's id, equal to the agent's `.meta.json` `toolUseId`), `<output-file>`, `<status>`, `<summary>`, a `<note>`, and possibly `<result>` and `<usage>`; the only parts read are `<tool-use-id>`, `<status>` (kept only as a word, 20 letters at most) and `<summary>`. The result, the output file and the rest are never read into the body.

Detection is at read time, on the prompt ops already recorded, by text plus launcher match (`readRecord` in `src/timeline/runs.ts`, `parseWake`). No hook field beyond `prompt` is used, and no new op field is needed. Ops written before this item read the same way.

Rules.
1. A wake is never a request: no "Your request" stop, not counted in the request numbering ("You made request n"), and its raw text is never shown.
2. The woken agent has its own lane even when it changed no file. A lane with no change gets one moment, "Helper n at work" (it cannot claim "changed no file" before the helper has finished). That moment is built where the helper starts, right after "Started Helper n", so it is timed at the launch and the helper's own calls follow it on its lane, never after them; a helper with no start step (resumed, or no launch call recorded) gets it at its wake instead. Its finish stop is the end. Tests: `test/timeline-helper-idle.test.ts` (shapes from recorded runs). The lane is the agent's own when any call of it carries the launcher id; with no call recorded at all it is a lane keyed by the launcher call.
3. The lane merges back into its spawner at the wake. The wake is a stop on the spawner's line reading "Helper n finished: <summary>" (the status is named, "Helper n finished (failed): ...", when it is not `completed`), and that stop is the lane's merge point. The summary goes through the same path scrub as every other line (a path outside the folder is cut to its name) and is cut at 300 characters. The page shows it by `textContent` only.
4. Claude's work after a wake belongs to the request that owns the woken agent (the request owning the launcher call), until the next request or the next wake. Work between a later request and the wake stays with the later request. On the time/step fallback path a wake-only turn adds its calls to the owner's request.
5. The spawner is the lane of the launcher call's agent: Claude's line for a main-line call, the parent helper's lane for a call made by a helper. A helper launched by another helper branches off and merges back into that parent helper's lane. A parent that has no lane (it changed nothing and was not woken) falls back up the chain to its own launcher, and ends at Claude. A foreground helper that changed nothing and was not woken still has no lane.
6. Helpers are numbered as before, from 1 in the order they first appear among the moments; a wake or the "changed no file" moment is a moment.

Detection is order-independent: the launcher is looked up after all ops are read. Batched notifications. The host can put several blocks in one prompt (see Structure). Each block that names a launcher call in the same session is a wake of its own (its own stop, its own merge). A block that fails the launcher check is dropped, its text shown nowhere, and it does not make the prompt a request. A prompt with no valid block is a request. Work after a batched prompt belongs to the owner of the last valid block's launcher (the request owning that launcher call), until the next request or wake; each wake itself stays with its own launcher's owner. Pinned by a test with blocks of two different owners, in both orders.

Several wakes of one agent. Every wake is a stop on the spawner's line, never a request. The lane merges at the first wake after the lane's last stop (an agent resumed by a message and finishing again merges at the later wake); with none after, at its first wake.

A nested helper whose parent has no moment before its first branches off the parent's branch point: the parent's own branch is moved up to the last stop (on the parent's parent, and so on up the chain) before the child's first moment, and the child leaves from the same stop. The renderer breaks a column tie by depth so a parent takes its column before the helper that leaves from the same stop.

Capture.
- A wake turn with no call (a read-only agent finishes and Claude only replies in text) still leaves its wake. The adapter logs a call-less turn's held prompts only when they start with `<task-notification>`; the ordinary typed request of a call-less turn is still dropped, deliberately and as before (it changed nothing, so there is no round to show it in). Only the wake is kept, so the wake stop and the merge appear. Pinned by the wake-adapter test.
- A background Agent or Task launcher is never an open writer. Its Post closes it like any call: its agent's work arrives through the agent's own hooked calls, so a change seen during a helper's own call goes to that call and lands on the helper's lane (before, the two launchers stayed open on `run_in_background` and were credited with the helper's write, which showed as "Claude changed ..."). A background Bash keeps the old rule: it stays open past its Post and is credited with files written after it. The op still records `background: true` on the launcher (the timeline uses it for the branch point below).

Where a background lane starts. A background launch is a point on the spawner's line. A lane whose launcher call is an Agent or Task with `run_in_background` leaves from the spawner's last stop at or before that launch, then runs alongside the spawner past its later stops until its merge at the wake (so the page shows that it ran during Claude's work, and overlapping lanes take separate columns: the renderer gives a helper the first column free over its span from the start stop to the merge stop, `review.js` columns). With no spawner stop before the launch (the agent was the request's first action), it still branches: from the stop of the request that owns the launch (exact, not the last request stop before it), else Start; the parent stays Claude's line and it is never a plain line. The renderer draws that branch because the start row is above the lane's first row (`review.js`: a start row at or below the first row is the only case that falls back to a plain line). A foreground helper is anchored at its launch too (below). A nested background helper leaves from its parent helper's last stop at or before that launch.

Where a helper's line leaves. A fork leaves from the later of two stops: the parent's last own stop before the launch, and the stop of the request that owns the launching call. Foreground helpers follow the same rule and are anchored at their launch, not at their first stop (this replaces the earlier foreground rule; a foreground launch with neither stop still gives a plain line). The owning request is exact: the launching call was made by Claude (not by a helper) inside that request's record, and no wake stop sits between the request stop and the launch (a wake turn has no request of its own). A helper launched by another helper, or in a wake turn, never takes a request stop: it leaves from its true parent's last own stop (a nested helper's parent is the helper, so its fork stays on the helper's line), else, for a background launch, from Start. Before this, the fork looked back only through the parent's own lane, so a launch that opened a request left above that request's row. Pinned by the launch-request test.

Background without the flag. Claude Code 2.1.296 runs some Agent calls in the background with no `run_in_background` in the Agent input; the tool result says "Async agent launched successfully" and the agent's `subagents/agent-<id>.meta.json` carries `requestShape: "background"` beside the `toolUseId` of the launching call. A launch is background when the input says so (`launchedInBackground`, `src/timeline/runs.ts`, Agent and Task only) or when that meta file says so (`markBackgroundLaunchers`, `src/agent-transcripts.ts`, run by `backfillAgentLanes` on the in-memory copy of the rows, so runs already recorded are fixed and stored ops are never rewritten). Such a lane branches at its launch by the rule above. A foreground helper, a meta file with no `requestShape` or another one, a meta file of another session, and a run without meta files place exactly as before. A lane with a merge point but no start stop still draws its merge back into its spawner (`review.js`): its top is a plain line and the merge curve is drawn as usual. A change credited jointly to several calls is placed by the time of its own step (`change.at`), not by the start of the first credited call, which can be a call left open across many later steps (a call whose Post never came): the jointly credited steps of one helper no longer collapse onto that call's start. A change credited to one call used to keep that call's start; that was replaced, see "A change sits at the time it was observed". The playhead line (`.ph`) is lifted by half its border so its centre is the node's centre.

Declared limits. Each is named against the clause it touches.
1. No capture-time flag is written (read-time detection covers it).
2. Batched blocks with different owners: all post-wake work goes to the last valid block's owner, not split by block (the rule is "until the next request or the next wake": the prompt is one wake event with one stamp).
3. The nested-branch drawing is checked at the model (start stop before the child's first moment, shared with the parent), not by a geometry test of the renderer (the nested-branch clause).
4. Whether the host's `<tool-use-id>` equals the agent's `toolUseId` rests on one real transcript; a host that differs leaves its notifications as requests (the safe direction) (Definition).
5. The notification is not escaped by the host, so the parse is a convention, not a grammar. Head: a `<summary>` or other head field that itself contains `<result>`, `<usage>` or `</task-notification>` ends the head early and can lose the id or cut the summary (Structure, fields at top level; the loss is a missed wake, never a changed launcher). Span: a result that reproduces `</result>` immediately followed by `</task-notification>` at balance 0 ends the block early; what follows is then read as blocks or as typed text. If it follows with a notification naming a real launcher of this session it makes a false wake for that launcher, and plain text after it becomes a false request (Structure, block ends). Producing that sequence takes an agent writing the host's exact closing sequence into its own output; no ordinary text does. A result with a lone unclosed `<task-notification>` swallows the rest of the prompt (a missed wake or lost trailing text, the safe direction).
6. Typed text after the last block is read as a request even if the user did not type it (for example a line the host appends); none is known (Text outside the blocks).
7. The rail's column assignment for overlapping lanes is read from `review.js`, not run: the model test asserts the lanes' spans overlap and share the start stop, and the vm page stub does not expose geometry (the background-lane clause).
8. A background lane with no spawner stop before its launch branches from the request stop, drawn at the Claude column on the request row (which carries no Claude line of its own), not from a Claude stop. The Start fallback has no test of its own: a call with no prompt still gets a text-less request stop, so only "start or that stop" is asserted. A foreground helper launched first keeps a plain line.

## A change sits at the time it was observed

Definition. A change sits on the rail at the time it was observed: its own observed time (`change.at`, the time of the file state that recorded it). It never sits at the start of a call that spans other observations. One function, `observedAt` (`src/timeline/rail/model.ts`), decides it for every kind of change: jointly credited and credited to a single call alike. A change with no observed time takes the start of the call that made it. A change never sorts before the start of the call that made it: an observed time earlier than that start is lifted to the start. Ties keep the order the timeline holds. The rail's before-tree of a change lists the files whose first change comes earlier in that order, so before-trees are built from the states at that time.

Why. A call left open across later steps (a long call, or one whose Post never came) must not pull its single-call change to the call's start: otherwise a file the call wrote last (a memo written last, c21) sorts before c19 and c20 though it does not exist yet, and c20's before-tree lists it.

Declared limits. The order of a change observed at the same instant as another is still the record order. A change whose state carries no time still sits at its call's start.

## Who made a change

Who made a change is decided once, by `attributionOf` in `src/timeline/attribution.ts`. It reads only the file state (`credited`, `calls_open`, `phase`), the calls CoCheck still has, and the task's host. The result is stored on each change as `change.by`, with a kind (`call`, `joint`, `lost`, `during` or `outside`), the calls, and whether the values expired. Every surface takes its wording from that module: the rail lane, chip, head and side text, the change and row notes, the page's who text and short who, the credit text, and the timeline's missing list. None of them reads `credited`, `unplaced` or placements to decide who made a change. CoCheck sees file content, not which process wrote it. A change reads as made outside the agents only if no call is credited, none was open when it was found, and it was not found at a call's Post. A change that any credited or open call could have made never reads outside. A change goes on one agent's lane only when every credited call is that agent's and every one of them is still on record. Otherwise it goes on the "Can't tell which" lane, which names the possible makers and nothing more.

The five kinds, with the actor a note starts with and the lane:

- `call`: one credited call on record, or several on one lane. The actor is the host's name (the call's host, else the task's host from the `<host>-hook:` prefix of the client name, else "The agent"), or "Helper n" on that helper's lane. Lane: the main lane (`claude`, named for the task's host) or `agent:n`.
- `joint`: credited calls on record on two or more lanes. The rail names them ("Claude or Helper 1"); the body, which does not number helpers, says "Claude or a helper". Lane: `unsure`.
- `lost`: credited, but some credited call has no record (expired or gone), including a mix of calls on record and gone. The actor is "An agent call whose record is gone". Lane: `unsure`. Expiry blanks the calls' ids, agents and hosts, so a lost change can't be matched back to its true lane; the side text names the host only when the task's client name proves it.
- `during`: no call credited, but calls were open when it was found (the Stop sweep with a background call still open, a record from before schema 12 whose `calls_open` held the calls), or it was found at a Post (a Post whose Pre was never seen, or whose call expired). The actor is "Something, during agent calls,". Lane: `unsure`.
- `outside`: no call credited, none open, and not found at a Post. The actor is "Something outside the agents". Lane: `other` ("Outside the agents"), with the side text "Changed between agent calls; CoCheck can't tell who or what wrote it (you, an app, or another process)." An outside change never names a host.

The `unsure` lane is named "Can't tell which", its chip is "?", it is grey (`#9aa0a6`), and the model lists it only when a change sits on it. Its side text names the possible makers: the joint lanes, the credited call whose record is gone (with the host when proven), or the calls that were running. A helper credited jointly gets its numbered lane even with no stop of its own, and is never shown as a helper that changed no file. The hook's own words on a file state ("not from an agent call", "calls were still open, but none can be shown to have made it") are cut from `change.ledgerNote`. Expiry blanks only values: `credited_json`, `calls_open_json` and `phase` survive, so an outside change still reads outside after expiry, and every credited change reads as `lost`. A body without `by` (hand-built) never reads outside.
