## Discrepancies

Read from `platforms/discrepancies.json`. Each entry names the platforms it concerns and the status of the fact behind it.

- Codex has no failure event (codex; confirmed, 2026-10-24): The hooks page lists 12 events (the source has 14, none a failure event) and no tool-failure one, so a failing Bash command arrives as PostToolUse. A Codex call that closes with no failure event is therefore not proof it succeeded, and the codex profile keeps failureEvent false. The shared event-name table still maps PostToolUseFailure for Codex; that entry is inert because it is never installed. Source: https://learn.chatgpt.com/docs/hooks
- Copilot has no call id in any hook payload (copilot-cli, copilot-vscode; confirmed, 2026-10-18): No tool call id, turn id or message id appears in a Copilot hook payload (tool events carry sessionId, toolName and toolArgs only). CoCheck takes the id from the session file or makes a synthetic one and binds a Post to the oldest open Pre with the same tool and arguments, so two identical concurrent calls can be paired the wrong way round. Source: probe:versions/1.0.93/hook-payloads/preToolUse.jsonl
- Copilot reads a repo's .claude/settings.json hooks (copilot-cli, copilot-vscode, claude-code; confirmed, 2026-10-24): Copilot CLI and VS Code load the hooks field of the repo's .claude/settings.json and .claude/settings.local.json. A hook CoCheck writes there for Claude Code (a repo-scope install) also runs under Copilot, with a different payload shape and no --host copilot flag, so it could record a Copilot session under the wrong host. Copilot does not list the user-level ~/.claude/settings.json, so a user-level Claude install is not read (by omission on the page, unverified). Source: https://docs.github.com/en/copilot/reference/hooks-configuration
- Cloud surfaces cannot reach the Mac (claude-code, codex, copilot-cli; confirmed, 2026-10-24): Claude Code cloud sessions, the Copilot cloud coding agent and Codex Work Cloud run on the vendor's machines. A command hook there cannot write ~/CoCheckData. Claude cloud sessions read only the repo's .claude/settings.json and no local or user-level plugins; Copilot cloud runs only .github/hooks/*.json from the default branch; Codex Work Cloud runs only admin-managed remote mcp_tool hooks. CoCheck sees only files that reach the Mac afterwards. Source: https://code.claude.com/docs/en/claude-code-on-the-web
- Codex 0.164.0 added two model-request events (resolved) (codex; confirmed, 2026-10-24): 0.164.0 (2026-10-23) has 14 hook events: the 12 on the docs page plus PreModelRequest and PostModelRequest (observation-only, PR #55144), which the hooks page still omits. PR #55657 is an in-process Rust extension trait, not a hook. Both new events fired live on 0.164.0-alpha.11.1. Source: probe:versions/0.164.0-alpha.11.1/hook-calls-run2.jsonl
- Two Claude pages disagree on a timed-out PreToolUse (claude-code; contradicted, 2026-10-24): hooks.md says a timed-out PreToolUse does not block unless onFailure is block; the Agent SDK page says it blocks the call with a hook-did-not-respond result (2.1.210 and later). A hook that must never block should set onFailure explicitly; a probe with a sleeping hook would settle it. Source: https://code.claude.com/docs/en/hooks
- Whether hook commands run inside the sandbox differs by host (codex, copilot-cli, copilot-vscode, claude-code; confirmed, 2026-10-24): Settled 2026-10-24: Codex hooks run outside the sandbox (source and live, write and localhost ok under workspace-write). Copilot CLI hooks run inside the sandbox when it is on (it is off by default); with --sandbox they fail open until sandbox.userPolicy grants the script and ~/CoCheckData. VS Code hooks wrote outside the workspace and reached localhost (sandbox state not recorded). Claude Code is still unknown. Source: probe:versions/0.164.0-alpha.11.1/hook-calls-run2.jsonl
- Copilot's built-in general-purpose subagent fires subagentStart and subagentStop (copilot-cli, copilot-vscode; confirmed, 2026-10-24): The hooks reference says the built-in general-purpose subagent fires no subagentStart or subagentStop. Live, it does on both Copilot CLI 1.0.98 and VS Code 1.140.0 (via the task tool), in the same shape as a custom agent. Source: probe:versions/1.0.98/hook-calls-camel.jsonl
- PascalCase PermissionRequest keeps a camelCase payload (copilot-cli, copilot-vscode; confirmed, 2026-10-24): The docs say a PascalCase-registered event switches to the VS Code format (snake_case fields). Live on CLI 1.0.98, PermissionRequest (and userPromptTransformed, which has no alias) stay camelCase: hookName, sessionId, toolName, toolInput with lowercase tool names, while PreToolUse, PostToolUse and the others switch. Source: probe:versions/1.0.98/hook-calls-pascal.jsonl
- Codex spawn tool name is collaborationspawn_agent, not spawn_agent (codex; confirmed, 2026-10-24): The docs say spawn_agent also matches Agent. In PreToolUse and PostToolUse on 0.164.0-alpha.11.1 the tool_name is collaborationspawn_agent (and collaborationwait_agent), namespace and name joined with no separator. Whether a spawn_agent or Agent matcher still matches it was not tested; do not match on the documented name alone. Source: probe:versions/0.164.0-alpha.11.1/hook-calls-run2.jsonl
- Claude Code: updatedMCPToolOutput versus updatedToolOutput is unresolved (claude-code; unverified, 2026-10-24): The hooks page names the PostToolUse rewrite field updatedToolOutput; the 2.1.296 changelog says managed PostToolUse hooks did not apply updatedMCPToolOutput. It looks like a rename or alias but no page says which, so the register records only the documented name. Source: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md
- VS Code docs list nine hook events but more fire (copilot-vscode; confirmed, 2026-10-24): The VS Code hooks page names nine events and defers to the GitHub reference for the rest. Live on 1.140.0, userPromptTransformed, permissionRequest and notification also fired (11 distinct events in one scripted session), so the earlier 'missing' list was documentation lag. postToolUseFailure and errorOccurred were not exercised and are unverified. Source: probe:versions/1.140.0/hook-calls-vscode.jsonl
- Copilot reports failing shell commands as success (copilot-cli, copilot-vscode; confirmed, 2026-10-24): A shell command that exits non-zero arrives as postToolUse with resultType success; the exit code appears only in the result text (<shellId: N completed with exit code 3>), and postToolUseFailure does not fire. postToolUseFailure fires only for tool-level failures such as viewing a missing path. A failure is visible only by parsing the text. Source: probe:versions/1.0.98/hook-calls-gh.jsonl
- Codex PostToolUse carries no exit code (codex; confirmed, 2026-10-24): For a failed command tool_response is the bare output string; there is no exit code, is_error or structure, and a success returns an empty string. A failure that prints nothing is indistinguishable from a success in the payload. Source: probe:versions/0.164.0-alpha.11.1/hook-calls-run2.jsonl
- Codex untrusted hooks and Copilot untrusted folders skip hooks silently (codex, copilot-cli; confirmed, 2026-10-24): Codex skips a hook that is untrusted or whose content hash changed, with no warning in stdout, stderr or any log; trust can be read through app-server hooks/list (trustStatus). Copilot CLI skips repo hooks from an untrusted folder with no trace until the folder is in trustedFolders. In both cases capture stops with no visible error. Source: probe:versions/0.164.0-alpha.11.1/run1-untrusted.err
- Copilot records a call twice when hooks sit in .github/hooks and .claude/settings.json (copilot-cli; confirmed, 2026-10-24): Both sources run and nothing de-duplicates, so a CoCheck install in both places records each call twice, in two payload formats (camelCase and snake_case). Source: probe:versions/1.0.98/hook-calls-gh.jsonl
- VS Code subagent calls carry no agentId (copilot-vscode, copilot-cli; confirmed, 2026-10-24): Copilot CLI marks every call inside a subagent with agentId and parentAgentId. VS Code 1.140.0 does not: inner calls arrive under the subagent's own sessionId and are linked to the parent only at subagentStop (agentId equals that sessionId) or via permissionRequest (which keeps the parent sessionId). Source: probe:versions/1.140.0/hook-calls-vscode.jsonl
- Claude Code docs list effort as a common field, the 2.1.302 recording lacks it on some events (claude-code; confirmed, 2026-10-24): The hooks reference lists `effort` ({level}) among the common fields. In the 2.1.302 recording it is present on PreToolUse, PostToolUse and Stop and absent from SessionStart, UserPromptSubmit and SessionEnd. Source: probe:versions/2.1.302/payloads.jsonl
- CoCheck does not support the Copilot cloud coding agent (copilot-cli; confirmed, 2026-10-24): Registered as unsupported (2026-10-24). The cloud coding agent runs on GitHub's runner, not on the Mac: a hook there cannot write the CoCheck data home or the person's folder, it runs only .github/hooks/*.json from the repo's default branch (bash entries only), and CoCheck's install is user-level (~/.copilot/hooks), which that agent never reads. CoCheck sees only the files that reach the Mac afterwards. See cloud-surfaces-cannot-reach-the-mac. Source: https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/use-hooks
- No hook channel puts the 'save in the folder' words in front of a Copilot session (copilot-cli, copilot-vscode; confirmed, 2026-10-24): Claude Code and Codex get CoCheck's context text as UserPromptSubmit output. Copilot's userPromptSubmitted has no output channel (modifiedPrompt is honored only by SDK hooks); sessionStart, subagentStart and postToolUse document an additionalContext output that was never observed to reach the model, and every session starts untracked, so sessionStart cannot carry words about tracking. CoCheck therefore sends nothing from a Copilot hook. The words reach the session through the cocheck skill that `cocheck install` writes to ~/.copilot/skills (the skill says the folder the person is in becomes the task folder and the files go inside it), read when the person says start tracking. Gap: a person who never loads the skill gets no such words. Candidate for later: postToolUse additionalContext on the `cocheck track start` call, untested. Source: https://docs.github.com/en/copilot/reference/hooks-configuration
- With Copilot's sandbox on, CoCheck's hook fails open unless the policy grants it (copilot-cli; confirmed, 2026-10-24): The sandbox is off by default. With it on (copilot --sandbox or /sandbox enable) every hook failed with exit 126 and Copilot carried on, so CoCheck recorded nothing, until sandbox.userPolicy.filesystem.readwritePaths in the person's settings.json granted the hook script and the data home. CoCheck never edits the person's Copilot settings: `cocheck install` and `cocheck status` print what to add (the CoCheck folder and the data folder). Gap: the person must make that change, and nothing detects a sandboxed session that records nothing beyond the 'not recording' note the launcher writes when it runs. Source: probe:versions/1.0.98/out-sandbox-no-policy.txt
- VS Code agent mode reading ~/.copilot/hooks is documented, not probed (copilot-vscode; unverified, 2026-10-24): CoCheck's one Copilot install is the user-level file $COPILOT_HOME/hooks/cocheck.json. The VS Code hooks page lists ~/.copilot/hooks as a source; the 1.140.0 probe used a repo .github/hooks file only, so a live VS Code session reading CoCheck's file is the real-use check, not a recorded fact. Source: https://code.visualstudio.com/docs/copilot/customization/hooks
- Codex failures are guessed from the output text (codex; confirmed, 2026-10-24): Codex sends no failure event and PostToolUse has no exit code, so CoCheck reads a command as failed only when every line of its output is a shell error line (such as 'No such file or directory'). That is a guess: a command that fails with no output, or with output that does not look like a shell error, shows as a success, and a command that prints only such lines and succeeds would show as failed. Source: probe:versions/0.164.0-alpha.11.1/hook-calls-run2.jsonl
- Codex install cannot trust its own hooks (codex; confirmed, 2026-10-24): CoCheck writes its hooks to config.toml but does not write Codex's trust record, because the hash Codex checks is Codex's own and no source in the register says how it is made. After an install or an update that changes the hook command, Codex skips the hooks until the person trusts them in Codex. cocheck status reads the trust state through app-server hooks/list and says so. Source: probe:versions/0.164.0-alpha.11.1/app-server-hooks-list.json
