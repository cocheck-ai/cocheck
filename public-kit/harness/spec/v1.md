# CoCheck harness specification v1

Status: v1, experimental. A harness is an AI agent program that runs tools on a person's behalf (a coding agent, a desktop agent, a command-line assistant). CoCheck learns what such an agent did to the files in a folder by listening to the hooks the harness runs around its calls. This page says what CoCheck reads from a harness, how a harness describes itself in one JSON file, and what CoCheck loses when the harness cannot say something.

You do not write code to add a harness. You write a manifest, record a real session, and write cases that say what CoCheck must make of it. `cocheck harness test` checks the two against each other.

## 1. The canonical event

Whatever shape a harness sends, CoCheck reads each hook call into one event, `NormalizedEvent` with `v: 1`. A consumer refuses any other `v`. Values pass through unchanged (never coerced), so an odd payload gives an odd value; CoCheck does not repair it.

### Kinds

| kind | meaning |
| --- | --- |
| `tool-pre` | a tool call is about to run |
| `tool-post` | a tool call finished |
| `tool-failure` | the harness's own event for a failed call |
| `stop` | the main agent finished a turn |
| `subagent-stop` | a helper agent finished |
| `prompt` | the person submitted a prompt |
| `file-edit` | a file the harness changed, reported on its own event (see "Per-action events") |
| `shell-pre` | a shell run is about to start (per-action) |
| `shell-post` | a shell run finished (per-action) |
| `session-start` | a session began; carried, nothing is recorded for it yet |
| `session-end` | a session ended; carried, nothing is recorded for it yet |
| `other` | an event name CoCheck does not act on, or one a `refine` rule demotes (for example a helper's own prompt) |

### Fields

Always present: `v`, `host` (the harness key), `kind`, `eventName` (the harness's own event name), `session`, `narratesBeforeCall` (true when the harness writes the call's words to its session file before the call), `sessionFileBySessionId` (the session file can be found from the session id alone), `extra`, `proof` and `synthetic`.

Present when the payload has them: `cwd`, `toolName`, `toolInput` (parsed when the harness sends JSON text), `toolResponse`, `toolUseId` (the call id), `agentId`, `agentType`, `failure` (`raw`, `interrupted`, and `inferred` when the failure was read from output text), `transcriptPath`, `lastAssistantMessage`, `prompt`. `extra` holds `turnId`, `permissionMode`, `model` and `stopHookActive` when the harness sends them. `proof` is empty and `synthetic` false for every harness today: the proof of who made a change is found by CoCheck's own check of the folder, not carried by the event.

A helper's events under its own session id carry the main session's id when the manifest names a `parentSession` field.

### Joining calls

A Post with the call id of a call already open in the same session closes that call. A second Post of a closed call adds nothing. A harness that sends no call id is given one made up per call (see `callId` below).

### Per-action events

A harness that reports each action on its own event instead of as a tool call maps those events to `file-edit`, `shell-pre` and `shell-post` and names, in `perAction`, the tool each stands for and where its parts sit in the payload. A `file-edit` is a call whose Pre and Post happen together: the change found in the folder since the last event is credited to it. A `shell-pre` is a tool Pre and a `shell-post` a tool Post for every rule after the entry. When a file edit is the first event in a folder, the file already holds the new text: its earlier state is rebuilt by undoing the reported edits (each new text found exactly once, and replaying the edits must give the file back), so the change shows. Bound: an edit that cannot be undone exactly (whole content only, a new text that is empty or found more than once) is found only as already present, and a rebuilt state never proves the edit.

## 2. Levels

A harness joins at the level its hooks allow. Each level is complete on its own and adds to the one before.

- **L0, a session.** The manifest names the session id. CoCheck knows a session exists and when its events came. It cannot say what any call did.
- **L1, calls.** Adds a Pre and a Post for each call, with the tool's name and its input. CoCheck compares the folder before and after each call and credits a change to the call that was open. Without a call id, ids are made up (one per call, in order), so overlapping calls cannot be told apart.
- **L2, adds the details that make the credit sound.** A call id the harness sends (`callId`), a failed call (`failure`), helper agents (`agentId`, `agentType`, `parentSession`) and the closing message (`lastAssistantMessage`). Overlapping calls and helpers are credited to the right call, a failed call is not credited as if it had worked, and the closing message is shown.
- **L3, first-party extras.** Reading the harness's own session file for each call's words, finding helper files, install editors and trust checks for configs that are not JSON. These are code in CoCheck, named in the `extras` list of a built-in manifest. A manifest in your own folder can name only the outsider-safe extras (section 5), so L3 is for harnesses shipped with CoCheck.

Each case file declares the level it exercises.

## 3. The manifest

One file, `cocheck-harness.json`, in a folder named after the harness key: `<key>/cocheck-harness.json`. It is JSON with `"schema": "cocheck-harness/1"`. It holds no code. A payload path is `a.b` or `a[0].b`: keys joined by dots, with `[n]` for a list position. A pattern is a regular expression of at most 200 characters, with no backreference, no lookaround and no repeated group that itself repeats or alternates (`(a+)+`). `cocheck` names the field of any error, for example `toyagent/cocheck-harness.json: events.beforeTool: unknown kind "tool-pree"`.

### Identity

- `schema`: `"cocheck-harness/1"`.
- `key`: lowercase letters, digits and dashes, at most 32. It must match the folder name and cannot be a key that already exists (the built-in harnesses, `both`, `all`, `none`, `unknown`).
- `displayName`: the name shown on pages.
- `fullName`: optional longer name.
- `chip`: the short mark drawn beside the name.
- `testedVersions`: the versions of the harness the recordings came from.

### Events

- `events`: the harness's event names mapped to a kind from section 1. At least one.
- `eventFrom`: where the event name is. `{ "payload": "<path>" }` when the payload names it, or `{ "arg": "--event" }` when the hook command names it (CoCheck then writes one hook entry per event, each passing its own name).
- `unverifiedEvents`: event names the harness documents but no recording shows. Declared, never mapped, never installed.
- `refine`: a list of rules that change an event's kind from the one its name maps to. Each has `kinds` (the kinds it applies to), `becomes` (the new kind), and one or both conditions, `whenPresent` (a path whose text is not empty) and `whenMatches` (`path` and `pattern`: the trimmed text at the path matches). Every given condition must hold; the first rule that holds wins.

### Where each value sits (`fields`)

`fields` maps a canonical field to a payload path. `session` is required; the rest are optional.

- `session`: the session id.
- `eventName`: only when the name is also read from a path your other fields need.
- `cwd`: the folder the harness is working in.
- `toolName`: the called tool's name.
- `toolInput`: the call's arguments.
- `toolResponse`: the call's result.
- `agentId`, `agentType`: the helper that made the call, when it was a helper.
- `transcriptPath`: the harness's session file, when the payload names one.
- `lastAssistantMessage`: the closing message, on the stop event.
- `prompt`: the person's prompt.
- `parentSession`: a helper's events carry the main session's id here.
- `callReason`: not a path: the key of the tool input that holds a per-call reason (`description`).

Related top-level fields:

- `toolInputEncoding`: `"json-text"` when the tool input arrives as JSON text, else `"object"` (the default).
- `callId`: where the call id is, with member `payload` (a path) or `synthesized`. `{ "payload": "<path>" }` when the harness sends one, `{ "synthesized": true }` when it sends none and CoCheck should make one per call in the session, or both (the harness's id when present, else made up). Left out: calls have no id.
- `extraFields`: paths for `turnId`, `permissionMode`, `model` and `stopHookActive`. Kept in the record; CoCheck does not act on them.
- `toolNameStrip`: `{ "prefix": "<pattern>" }`, a pattern matched at the start of the tool name and taken off (for a harness that joins a namespace onto the name).

### Failure (`failure`)

A failed call, per kind: `"tool-failure"` (the harness has its own failed-call event) and `"tool-post"` (a failed call arrives as an ordinary Post). Each holds a rule:

- `flags`: payload paths; the call failed when any holds `true`.
- `text`: paths; the failure's own words are the first that holds text.
- `nonEmpty`: for a `tool-post` rule, `true`: the call failed when `text` gives words that are not empty. For a harness whose Post carries an error field that is empty when the call worked. It needs `text`.
- `flaggedText`: where the words are when `text` gave none and a `flags` path is `true`. Each entry is a path, or `{ "path": "<path>", "blocks": true }` (with `blocks`, the value is a list of `{ "text": ... }` blocks, joined by a line break).
- `interrupt`: a path; `true` there marks the call as interrupted.
- `exitCode`: for a `tool-post` rule: `{ "from": "<path>", "pattern": "<pattern>" }`. The failure is a nonzero exit code stated in the text at `from`; the pattern has one group holding the code, and the last match wins.
- `inferred`: `true` when the failure was read from output text and not sent by the harness: a guess, never proof that other calls succeeded.

### Tools (`toolClasses`)

`toolClasses` names each tool the harness reports and what it does, as a `class`, so that CoCheck's rules never test a tool's name. A tool missing from the table is unknown: CoCheck reads nothing from its input (no named file, no command, no helper), and a change found in the folder while its call is open is still credited to it, on the basis `inferred`, as for any call. Unknown is the safe direction: a tool that writes without being listed (an MCP tool, a tool added in a new harness version) keeps its credit. To say a tool never writes, list it as `never-credited` (or `read`, `read-only`). Classes:

- `write`: writes a whole file from content.
- `edit`: changes a file by replacing text in it.
- `notebook-edit`: changes a notebook's cells.
- `patch`: carries a patch whose headers name the files it changes.
- `shell`: runs a shell command.
- `launcher`: starts a helper agent.
- `wait`: waits on helpers and writes nothing.
- `read`: reads a file by path.
- `read-only`: looks at files or the folder and writes nothing.
- `never-credited`: never writes a file in the folder (bookkeeping, web and messaging tools).

Each entry may add:

- `dialect`: for `shell`, `"bash"` or `"powershell"`: how the command is read.
- `waitFlag`: for `wait`, the input flag that makes the call a wait.
- `anyCase`: the tool name varies in letter case, so it is matched in any case.
- `pathFields`: for `write`, `edit`, `notebook-edit`, the input fields that name the file, in order.
- `pathChecked`: for `write` and `edit`, a call whose input names an absolute file is credited only with that file.
- `fileInput`: the input has the file-tool shape (`file_path` plus `content`, `old_string` or `new_string`).
- `backgroundFlag`: for `launcher`, the call runs its helper in the background when its input says `run_in_background: true`.
- `resumesHelper`: a call that wakes a helper that already ran.
- `backgroundable`: for `shell`, the command can leave a process running past the call's result, so its text is read for detach forms.

### Per-action events (`perAction`)

For a harness that maps events to `file-edit`, `shell-pre` or `shell-post`: `fileEditTool` and `shellTool` (names in `toolClasses` that those events stand for), and `fields` with `editPath` and `command` (required), and optionally `editList` (a list of edits), `editContent` (the file's whole new content), `exitCode` and `output`.

### Words and the session file

- `narration`: where a call's words and the closing message can be read. `sources` is a ranked list; each has a `kind` (`text-before-call`, `commentary-before-call`, `closing-message`), `readableAt` (`"pre"` or `"post"`) and optional `reason` (`true`: the words are also the call's reason). `closingWaitMs` is how long a stop waits for the closing message to reach a session file that lags the hook. A plain manifest reads the closing message from `lastAssistantMessage`; reading a session file for the rest is an L3 extra.
- `sessionFile`: where the harness's session file is, from the session id alone: `bySessionId`, `defaultRoot` and `file` (path templates; `{home}` and `{env:NAME|fallback}`, and in `file` also `{root}` and `{session}`). `file` is needed when `bySessionId` is true.

### Capabilities and other hosts

- `capabilities`: what the harness lacks or has, each `true` or `false`: `failureEvent` (it sends a failed-call event, so a call that closes with none succeeded), `argvTag` (its Pre hook can rewrite a shell call; built-in only), `helperSessions` (helper events arrive under the helper's own session id), `launchKey` (its payload may carry a key that binds a helper launch to its calls), `readsForeignHooks` (it also runs another harness's hooks).
- `foreignHookFingerprint`: for a harness that also runs another harness's hooks: `present` (keys that must be there), `strings` (keys that must be text) and `absent` (keys that must be missing), the payload shape of such a run. Another harness's hook that receives a matching payload records nothing (this harness's own hook records it). For a built-in harness the shape alone decides; for a harness in your own folder the fingerprint counts only while this harness's own CoCheck hook is installed for the payload's folder (section 5).
- `readsConfigsOf`: the harnesses whose config files this one also reads.
- `argvTag`: how a shell call is tagged so the change is proven: `tool`, `preOutput`, `envFileVar`, `shellEnv` and `sessionStartEvent`. Built-in only.
- `sessionEnv`: the environment variable the harness sets in the shell of its session to the session id.
- `hostOwnedFiles`, `hostOwnedWhat`: folder-relative files the harness's own app writes for its bookkeeping, and what the app is probably doing when it writes them (said after "Probably ").
- `shape`: the fields each event is expected to carry. Not read yet.

### Install (`install`)

What `cocheck install --for <key>` needs. For a harness in your own folder, install prints the config path and the hook entries to add instead of editing (section 5).

- `skillRoot`: the folder under the person's home where the harness reads skills.
- `hostFlag`: the `--host` value written into the hook command.
- `projectDirEnv`: the environment variable the harness sets to the project folder.
- `folderFromPayloadCwd`: the payload's `cwd` is the task folder, used when the command names none.
- `promptContext`: `false` when the hook must print nothing at a recorded prompt.
- `ownsFile`: the config file is wholly CoCheck's (uninstall deletes it, only when it carries CoCheck's marker).
- `inBothAlias`: the harness is part of what `--for both` means. Built-in only.
- `reusesRecord`: the harness's hook has no `--folder`, so an install reuses `--home` and `--folder` from the record of a first install.
- `timingLabel`: the harness's name in the hook-timing line, when it differs from `displayName`.
- `afterInstall`: said after an install, when the person has a step to take before the hooks run.
- `notes`: a note printed after install (`{launcherDir}` and `{home}` are filled in).
- `checkPayload`: `{ "payload": {...}, "event": "<name>" }`, a harmless Pre in the harness's own shape that proves the hook records (`{folder}` in a string is the task folder).
- `editorExtra` and `events`: a first-party editor for a config that is not JSON, and the hook events it installs. Built-in only.

The JSON hook-config editor is described by these members of `install`:

- `format`: `"json"`.
- `path`: the config file, a template: `{home}` (the person's home), `{project}` (the task folder, for a harness whose hook config sits in the workspace, such as `{project}/.cursor/hooks.json`), `{env:NAME}` (a variable that must be set) and `{env:NAME|fallback}` (the fallback a template itself). Any other token is refused when the manifest loads. With `{project}`, install uses the folder given by `--folder` (else the folder it runs from), and `cocheck harness record` uses its scratch work folder.
- `mode`: `"merge"` (edit the person's file, keeping everything else) or `"owned"`.
- `rootKey`: the top-level key holding the hooks.
- `envelope`: extra top-level keys for a new file, such as `{ "version": 1 }`.
- `events`: the event names CoCheck installs.
- `entryTemplate`: the entry written per event; `{command}` and `{event}` are filled in.
- `entryTemplates`: optional, an object from event name to an entry, for a harness whose config takes a different entry shape for some events (a group with `hooks` for tool events, a plain handler for the rest). A listed event uses its own entry; every other event uses `entryTemplate`. Each key must be in `events` or `extraEvents`, and each entry must use `{command}`. Install, uninstall and the missing-hook check read each event in its own shape.
- `matcherEvents`: events whose entry carries a matcher, and its value.
- `eventInCommand`: the command names its event as an argument.
- `failOpenEvents`: events whose hook must exit 0 even when CoCheck fails.
- `windowsCommandKey`: the key holding the Windows variant of the command.
- `extraEvents`: events written on install and removed on uninstall that are never reported missing.
- `managedHost`: an entry is CoCheck's when its command parses as a command for this harness.

### Extras

- `extras`: a list of first-party code the manifest opts into by name. An unknown name fails validation. The extras a manifest in your own folder may name are the outsider-safe ones: `codex-display-text` (turns a reply's file-citation directives into plain words). Every other extra reads files of a built-in harness or edits its config, and is for built-in manifests.

## 4. What degrades without each field

CoCheck never refuses a harness for lacking a field; it records less, and says so. This table is what is lost.

| missing | what CoCheck does instead |
| --- | --- |
| `fields.session` | the manifest is refused: nothing can be grouped |
| `events` for the call events (`tool-pre`, `tool-post`) | L0: the session is known, no call is recorded, no file is credited |
| `fields.toolName` | calls are recorded without a name; no tool can be classed, so every call is read as an unknown tool: credited only by what changed in the folder while it was open |
| `toolClasses` entry for a tool | that tool is unknown: its input is not read (no named file, no command, no helper launch), and a change while its call is open is credited to it by inference alone; list it as `never-credited` to stop that |
| `fields.toolInput` | the call's arguments are not read: a write tool's named file and a shell call's command are unknown, and the credit rests on what changed in the folder while the call was open |
| `callId` | calls carry no id from the harness, so calls that overlap cannot be told apart; `{ "synthesized": true }` makes one per call, which is sound only for calls that do not overlap |
| `failure` | a failed call looks like one that worked, and may be credited with a change it did not make |
| `capabilities.failureEvent` false and no `tool-post` failure rule | a call that closes with no failure is taken as succeeded, though it may not have been |
| `fields.agentId`, `fields.agentType`, `fields.parentSession` | helper agents' calls are credited as the main agent's; a change by a helper is not told apart from a change by the main agent |
| `capabilities.helperSessions` false | a helper's events are not linked to the main session |
| `fields.lastAssistantMessage` | no closing message is recorded at a stop, unless a first-party extra reads it from the session file |
| `narration` | a call's words are not shown beside the call |
| `fields.cwd` | the task folder comes from the hook command (`--folder`), or from `install.projectDirEnv`; with neither, the hook has no folder |
| `fields.prompt` | the person's prompt is not recorded |
| `fields.transcriptPath` and `sessionFile` | the session file is not read: no per-call words, and no check that every call was seen |
| `fields.toolResponse` | the call's result is not kept (CoCheck reads it only to keep an MCP call's response) |
| `install` | `cocheck install --for <key>` has nothing to write; the person adds the hook entries by hand |
| `perAction` for a per-action kind | the manifest is refused: a `file-edit`, `shell-pre` or `shell-post` event needs it |

An event the harness sends that the manifest does not map is kind `other`: it is journaled and not acted on.

## 5. Outsider policy

A manifest has two homes.

- **Your own folder.** Put it at `<CoCheck data home>/harnesses/<key>/cocheck-harness.json` (`$COCHECK_HARNESS_DIR` replaces that folder) to try a harness at once. It is loaded as an outsider.
- **A pull request.** Add it under `harnesses/<key>/` at the root of the CoCheck repository (a data folder that ships in the package; no code change) together with its recordings and cases, to ship it built in.

What a harness in your own folder gets, in v1:

- Its events never prove more than "inferred". A change is credited to that harness's call by what changed in the folder while the call was open, and never as a change the harness reported itself or one a tag proves. Built-in harnesses may earn the stronger bases (`host-reported-edit`, `argv-tag`); the same manifest, once shipped built in, may too.
- It may not tag shell calls (`argvTag`, `capabilities.argvTag`) or claim `install.inBothAlias`. A manifest that does is skipped with one plain line.
- Its `foreignHookFingerprint` (with `capabilities.readsForeignHooks`) makes another harness's hook skip a payload only while its own CoCheck hook is installed for the payload's folder: the config at `install.path` (with `{project}` set to the folder the payload names through `fields.cwd`) exists and carries CoCheck's entry for every event in `install.events`. Otherwise the payload is recorded as before. `cocheck status` names each fingerprint in force.
- `cocheck install --for <key>` prints the config path and the hook entries to add instead of editing the harness's config.
- It names only outsider-safe extras (section 3).
- Every pattern is bounded (section 3), and the text a pattern runs against is cut at 4096 characters.
- It cannot reuse a key that exists.

A manifest that does not load is skipped with one line (shown by `cocheck status`, and kept in the data home as `harness-skipped.txt` by the hook). Every other harness keeps recording.

## 6. Cases

A case is one JSON file, `cocheck-harness-case/1`: a recorded run, the files it needs, and what CoCheck must make of it. `cocheck harness test --cases <dir> [--manifest <path>]` replays each case through the real hook path in a temporary data home and folder (your own data home and configs are never read or written), then checks the result. `--manifest` is the manifest of a harness that is not built in; the built-in harnesses use the manifests that ship.

```json
{
  "schema": "cocheck-harness-case/1",
  "harness": "toyagent",
  "description": "one plain sentence",
  "level": "L2",
  "recording": [
    { "event": "beforeTool", "stdin": "<the payload text exactly as the hook received it>", "argv": ["--event", "beforeTool"] }
  ],
  "files": {
    "before": { "data.txt": "a,b,c\n" },
    "writes": [ { "afterEvent": 3, "path": "notes.txt", "content": "alpha\n" } ]
  },
  "expect": {
    "normalized": [ { "kind": "tool-pre", "session": "s1", "toolName": "write_file" } ],
    "credit": { "notes.txt": { "creditedTo": "call:<call id>", "basis": "inferred" } }
  }
}
```

- `recording`: the hook calls in order. `stdin` is the payload text; `<folder>` in it stands for the temporary task folder and `<root>` for the temporary root. `argv` holds the extra words of the hook command (the harness's `--event <name>` when its payload does not name the event).
- `files.before`: files in the task folder before the first call. `files.writes`: a file the harness's call left behind, written right after the recorded call number `afterEvent` (counting from 1), because a recording holds no file contents.
- `expect.normalized`: one entry per recorded call, in order. Each lists fields the normalized event must have (`kind`, `eventName`, `session`, `toolName`, `callId`, `agentId`, `agentType`, `prompt`, `lastAssistantMessage`, `failure`); an empty entry checks nothing for that call. An entry may list any field of the event.
- `expect.credit`: for each listed file, the call it ends up credited to (`call:<call id>`; several are joined by commas; `unattributed` when no call) and the basis (`inferred`, `host-reported-edit` or `argv-tag`). A file not listed is not checked.
- A case must credit at least one file, or say in its `description` why its level has none, using the words "no credit". A case that checks no credit gives false confidence.

`cocheck harness test` prints one line per case, `pass` or `FAIL` with the first difference in plain words, and exits non-zero if any case fails.

## 7. Versioning

The manifest and the cases are v1. A field added later is optional. A manifest with a `schema` this CoCheck does not know is skipped with a line naming it.
