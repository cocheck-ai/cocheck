# CoCheck change document v1

Status: v1, experimental. One document describes what changed between two states of an item, in the same shape for every product. It comes in three levels. Each level is complete on its own: a connector can stop at level 1 and still be fully drawn.

A change document is one JSON object. The spec field is `"cocheck.changes/1"`. `changes` is the list. The document does not say which level it is: the level is the one the connector declares in its `hello`, and the check is told it. `pictures` (level 2 and up) and `caveats` (a list of sentences about what was not compared) are optional. The check is `checkChanges` in the CoCheck source; it names the field path of every problem.

## The three levels

1. **Level 1, a change list.** Each change has a `label` (where it is, in words), a `mark`, and `before` and `after` in words. CoCheck draws each as a card. No pictures, no boxes.
2. **Level 2, adds pictures.** `pictures` lists what can be shown for each side. A picture has an `id`, a `side` (`before` or `after`), a `type` and an optional `src`. Pictures are shown beside the cards; nothing is outlined yet. A picture's contents are its `src` (an `image`); CoCheck draws no grid or text from a document's own fields in v1, so a `grid` or `text` picture a stranger sends is a name for where the boxes sit, and its changes are listed in words (see "What always draws" below).
3. **Level 3, adds anchors.** A change may carry `boxes`, each placing it on one picture, and `unplaced`, the words for a side that exists but has no place ("not marked"). A box above level 3 is a problem, and so is a picture above level 2.

A box names a picture, takes that picture's side, and its anchor must be of that picture's system. Every change keeps its level-1 fields at every level, so a level-3 document degrades to level 2 or 1 by deleting fields.

## The change

| field | meaning |
| --- | --- |
| `id` | unique within the document |
| `mark` | one of the five marks below |
| `label` | where the change is, in words (`"Sheet1!D5"`, `"paragraph 7"`, `"Slide 2 / Title 1"`) |
| `before`, `after` | the old and new content in words; leave out the side that does not exist |
| `parent` | the `id` of the change that contains this one, or `null` |
| `text` | optional: one plain sentence of what changed, for a change whose words do not fit `before` and `after` ("Moved from position 2 to 3", "Picture resized") |
| `lines` | a list of sentences stating consequences ("Items below renumbered 2 to 1") |
| `kind` | an open string the product may use for its own sort of change. CoCheck does not read it: no value of `kind` changes how a change is drawn or counted |
| `private` | an opaque object for the product's own data. Not read by the check beyond being an object |
| `boxes` | level 3: where the change sits on pictures |
| `unplaced` | level 3: `{ "before"?, "after"? }`, words for a side with no box |

`changes` is in reading order, the order the reviewer should see them. CoCheck opens a step on the first change, in this order, that has a box it can draw, and Next change follows the order. A document with pictures but no boxes opens on the first picture marked `changed: true`; a document with words only shows its first change first.

## The picture

| field | meaning |
| --- | --- |
| `id` | unique within the document |
| `side` | `before` or `after` |
| `type` | `image`, `grid`, `text` or `html`; the type fixes the anchor system, from the anchor table below |
| `src` | where the picture comes from (a path or address), optional |
| `label` | optional: the picture's name in words, such as a tab or a caption ("Before, page 2 of 5") |
| `width`, `height` | optional: the picture's size in pixels, so an `image` box (`rect`, `highlights`) can be placed on it |
| `note` | optional: one sentence drawn under the picture ("CoCheck's sketch of the chart, not Excel's drawing") |
| `absent`, `unchanged`, `reflowed`, `changed` | optional flags, `true` when set. `changed`: the product has changes on this picture, whether or not each one has a box (a sheet whose changed cells are all past what is drawn). `absent`: the other side has this page and this side does not. `unchanged`: the page was compared and matches. `reflowed`: its words are the same but the page breaks moved |
| `private` | an opaque object for the product's own data. A connector keeps the data its own pages need here (the built-in Excel, Word and PowerPoint connectors do the same, on the same terms); a document that does not carry it is still drawn in full (below). Nothing in `private` is part of the standard |

## The five marks

- `added`: the change exists after and not before.
- `removed`: it exists before and not after.
- `changed`: it exists on both sides and differs.
- `moved`: the same thing is somewhere else.
- `described`: a change that can be described in words but has no visible place. A `described` change is shown as a card only.

## What always draws

Every change in `changes` reaches the page, as a card or as a row of the words list, whatever else the document holds. A change with no box, or whose boxes sit on a picture CoCheck cannot draw from the document alone (a `grid` or `text` picture with no `src`, an `image` with no `src`, an unreadable `src`), is listed in words, "not marked" on that side. A cell box is counted as drawn only where a grid is actually drawn for it. Nothing about a change is hidden because of a field the page does not know: the reserved words the page once looked for in `kind` (`card`, `card-paragraph`, `region`, `notes`, `paragraph`, `cell`) and in picture ids (a `/notes` suffix) are ordinary values and ordinary ids, and a change that uses them draws like any other.

## The three anchor systems

Every picture has a `type`, and the type fixes the anchor system (a picture does not carry a `system` field):

| type | system | what a box carries |
| --- | --- | --- |
| `image` | `pixels` | `rect` `{ x, y, w, h }` in picture pixels, and/or `highlights`, a list of such rectangles |
| `grid` | `cells` | `cell`, a cell or range such as `"B3"` or `"B3:D7"` |
| `text` | `text` | `lines` `{ from, to }` (1-based, inclusive) or `range` `{ line, start, end }` (character offsets in that line) |
| `html` | `none` | no box. An `html` picture can be shown but not anchored in v1 |

A box is `{ picture, <one anchor> }`, where `picture` is the id of a picture; the box is on that picture's side. A `rect` or `highlights` on a grid, a `cell` on an image, `lines` or `range` off a text picture, or any box on an html picture is a problem.

## General fields (v1.1)

Optional fields any connector may use. A document without them is valid, as before. Each is checked by `checkChanges`; none changes how an older document is read.

| where | field | meaning |
| --- | --- | --- |
| document | `status` | `{ "kind": "refused" \| "prompt" \| "hang" \| "crash" \| "unavailable", "evidence": "<opaque text>" }`: why the product could not be read. CoCheck shows `evidence` and reads nothing into it |
| document | `pendingRetry` | a whole number from 1 to 5: the product is not ready, ask again; the count is how many more times, and it is never above 5 |
| picture | `status` | the same object, for a side that could not be drawn |
| picture | `renderedBy` | `{ "tool", "version", "os" }`, three non-empty strings: what drew the picture |
| picture | `page`, `pageCount` | whole numbers from 1: this picture is page `page` of `pageCount` (`pageCount` is not below `page`) |
| picture | `hidden` | `true`: the picture is kept in the document but not shown by default |
| picture | `group` | a non-empty string: pictures with the same `group` are one before-and-after set, and the page shows them together, before beside after, whatever their place in `pictures`. Use it when the n-th picture of one side is not the n-th of the other (content inserted, one picture per change area). A group may hold any number of pictures on each side, including none; groups are shown in the order of their first picture |
| picture | `order` | a whole number from 0, only with `group`: the picture's place on its side of the group. The page puts the pictures of a group with the same place side by side, and shows pictures of one set at the same scale |
| picture | mate (level 3) | how `cocheck connector test` finds the other side's picture for the pixel check of a box: a picture with a `group` is paired with the one picture on the other side with the same `group` and `order`; none, or more than one, means no pairing and no pixel check (a `looksSame` box is then not accepted). A picture without a `group` is paired with the picture on the other side with the same `label`, else the only picture on that side. When the same change has exactly one box on the picture and exactly one on its mate, each side is read under its own rect; with more than one box on either, both sides are read under the same rect |
| change | `causedBy` | the `id` of another change in the document that caused this one |
| box | `looksSame` | `true`: the box points at something whose pixels are the same on both sides. Accepted only over identical pixels: over differing pixels, or where the pixels cannot be compared, `cocheck connector test` fails the box |
| manifest `requires` | `session` | `"desktop"`: the connector needs a logged-in desktop session. When this machine is not one, `cocheck connector test` prints `unverified` and runs nothing |

## General fields (v1.2)

Optional fields any connector may use. A document without them is valid, as before, and draws as before. The spec id stays `cocheck.changes/1`. Each is checked by `checkChanges`; an absent field is always valid, and a long list is never refused.

| where | field | meaning |
| --- | --- | --- |
| document, picture, change | `issues` | a list of `{ "text", "side"?, "where"? }`: problems the connector found in a state it read, either something the app would complain about or a value the change broke. `text` is a non-empty string, the problem in the connector's words; `side` is `"before"` or `"after"`; `where` is a short non-empty label in the connector's words. What the connector did not compare is a `caveat`, not an issue; a side that could not be read is a `status` (document or picture) or an error answer |
| document | `more` | a whole number from 0: how many changes are not listed at all |
| change | `more` | a whole number from 0: how many children of this change are not listed |

How the page draws them. Issues from every level of the document are one quiet count on the step ("2 issues") that opens the list; an absent or empty list shows nothing. Issue text is outside data: it is drawn as text, never as HTML, at most 50 entries of at most 300 characters each, then "and N more". `more` is drawn as "and N more" in place: after the list for the document, inside the change for a change. The page adds no place name of its own ("sheet", "slide"): the connector's labels say where.

The nothing-changed rule. A connector opts into it by declaring `"nothingChanged": true` in its `hello` answer. CoCheck records the declaration with each document it freezes (`"nothingChanged": true` in the `source` envelope), so a document frozen without it never gets the line. Without the declaration an empty `changes` keeps its v1.1 meaning: nothing is listed, and nothing is claimed; the page shows no "Saved again" line for it. A connector that declares it answers an empty `changes` only when it compared everything it can see in the two states. When the two states differ in anything it does not model, it lists one `described` change in its own words (for example "the workbook changed in ways this change list does not show"). Under this rule, an empty `changes` with no picture means "saved again, nothing changed", and the page says "Saved again: nothing changed.". With pictures, each `unchanged`, the page says "Nothing visible changed: both versions look the same.", as in v1.1, for any connector: the pictures show it. An empty list does not count as nothing changed when the document also has a `status`, `pendingRetry`, a `caveat`, or a `more` above 0, or a picture not marked `unchanged`. A file created or deleted is not a re-save.

## Manifest additions

Three optional fields in `cocheck-connector.json`:

- `beforeReadMs`: how long, in milliseconds, CoCheck waits for the connector to read the "before" state. A whole number from 0 to 3000. When absent it is 1500.
- `diffMs`: how long, in milliseconds, CoCheck waits for the answer to one `diff` or `export` request. A whole number from 1 to 60000. When absent it is 10000. `cocheck connector test` honours it too.
- `permissions`: `{ "env"?: [string] }`. `env` is the list of environment variable names the connector may read; CoCheck starts it with those and a fixed base set, nothing else. The fixed base set is `PATH`, `HOME`, `USERPROFILE`, `TMPDIR`, `TEMP`, `TMP`, `SystemRoot`, `COMSPEC`, `PATHEXT` and `LANG`, copied from CoCheck's own environment when it has them, plus `COCHECK_HELPERS_DIR`, which CoCheck sets itself (see [Helpers](#helpers)) and never copies.

`openInProduct`, `permissions.network` and `permissions.files` are not part of v1: CoCheck never drew a link or enforced a network or file rule, so a manifest that has them is refused, not ignored.

A manifest without these fields is valid as before.

`matches.extensions` is the claim field: the file types the connector claims to view, as file endings (`.notes.json`). A claim says the connector can show that type; whether it is used for it is the per-type enabled rule in [One winner](#one-winner). Built-in connectors, the ones that ship inside CoCheck, declare their claims the same way and follow the same rule.

## Helpers

CoCheck publishes the general helpers its own connectors use, as plain JavaScript modules with type files (`.mjs` plus `.d.mts`), in `public-kit/helpers/`. CoCheck draws and checks with these same files, so a connector that loads them reads pictures and pages exactly as CoCheck does.

CoCheck starts every connector process, built-in or installed, with the environment variable `COCHECK_HELPERS_DIR` set to the absolute path of that folder in the running CoCheck. Load a helper from it at run time, never from a path of your own:

```js
import path from "node:path";
import { pathToFileURL } from "node:url";
const { decodePng } = await import(pathToFileURL(path.join(process.env.COCHECK_HELPERS_DIR, "png.mjs")).href);
```

| module | exports | what it does |
| --- | --- | --- |
| `png.mjs` | `decodePng`, `sameRegion`, `sameRegionAt`, `MAX_PIXEL_BYTES` | reads an 8-bit, not interlaced PNG (grey, grey and alpha, RGB, RGBA or palette) to RGBA pixels, and compares rectangles of two pictures; anything it cannot read is `undefined`, never a match |
| `pdf.mjs` | `renderPdfPage`, `pdfpagesPath`, `windowsPdf`, `createWindowsPdf`, `WINDOWS_PDF_SCRIPT` | `renderPdfPage(bytes, n)` draws page `n` (from 1) of a PDF as a PNG at two pixels per point, or gives `null`. On macOS it runs the `pdfpages` program CoCheck installs; on Windows, the system's PDF reader; on any other system it gives `null` |
| `pdf-text.mjs` | `readPdfText`, `findPdfParagraphs`, `cropPdfPage`, `pdfTextAvailable`, `pdfJsPath`, `inkBox`, `encodePng`, `CHILD_FLAG` | reads a PDF on any system with the pdf.js copy CoCheck ships; it is the reader CoCheck itself uses on every system: `readPdfText(bytes)` gives each page's size (two pixels per point) and its text runs with rectangles (per-letter `chars` on runs of capitals, digits and spaces); `findPdfParagraphs(bytes, queries)` places a document's paragraphs, in order, on its pages; `cropPdfPage(bytes, n, padPt)` cuts page `n`, drawn by `pdf.mjs`, to what is printed on it. pdf.js runs in a child process with a time limit; anything it cannot read is `null` |
| `pdf-text-layout.mjs` | `layoutPage`, `pageRuns`, `lineRects`, `normUnits`, `findInPages`, `SCALE`, `GAP_EM`, `BACK_EM`, `BULLET_EM` | the pure page model behind `pdf-text.mjs`: pdf.js text items to lines, runs and the paragraph finder |
| `spec.mjs` | `CHANGES_SPEC` | the `spec` value of a change document, `"cocheck.changes/1"` |

The variable is always set when CoCheck starts the connector, `cocheck connector test` included. A connector started some other way does not have it.

## What a connector sends

A connector's `diff` (entry `state` or `both`) and `diffs` (entry `diff`) may answer a change document. `hello` declares the level it answers, `"level": 1`, `2` or `3`, in place of the old `precision`. CoCheck checks every answer with `checkChanges`; the document may be at the declared level or below, never above. CoCheck freezes the document when the change is captured and never asks the connector for it again. A connector process may answer many diffs and must answer each from its inputs only. For a file on a claimed ending, the capture is done by CoCheck's long-lived review process after the agent's hook has recorded the write (both sides of the file are already kept), never inside the hook; if that process is not running at the write, the change is captured the first time its step is loaded. A connector that times out or fails leaves the step with the reason, and it is not asked again. The page gets the same document Office views get, plus a `source` envelope field saying who drew it:

```json
{ "by": "connector", "name": "toy-notes", "level": 1 }
```

`by` is `"connector"` (the connector sent the document, which is every connector that answers a diff, the built-in Office ones included) or `"cocheck"` (CoCheck drew the picture: export mode only); `name` is the connector id; `level` is the level of the document. The page says "Change list from <name>" for level 1, "Drawn by <tool>" for levels 2 and 3 (the `renderedBy.tool` of the document's pictures; with none, no line), and "Drawn by CoCheck from the text" for export mode.

A grid picture may carry `rows` and `cols` (whole numbers, its size in cells) so a `cell` box can be checked against it.

## Export mode

A manifest with `"entry": "export"` names a connector that does not diff. CoCheck calls the method `export` with `{ "subject": "..." }`; the connector answers `{ "text": "..." }`, the item as plain text, or `{ "text": null }` when the item does not exist. CoCheck stores the text of the before and after states and draws the difference with its built-in text renderer; the row's `source` is `{ "by": "cocheck", "name": "<connector id>", "level": 3 }`. An export connector declares no level. A malformed product state is answered with an error, never with empty text.

## Conformance per level

`cocheck connector test <dir>` grades a connector that declares a level at that level and prints the level passed (`level 3 passed`, or `level passed: 2 (declared 3)` and exit 1). The checks are exactly these:

- Levels 1 and 2: the document is valid at the declared level (`checkChanges` at the level `hello` declares: nothing above it, no picture at level 1, no box below level 3; a declared level the documents never reach fails, and the test prints the level the documents hold); and the same pair answered again gives an identical document (five runs).
- Level 3 adds: every box resolves in its picture's system (an image `rect` or `highlights` rectangle is inside the picture's `width` and `height`; a grid `cell` is inside the picture's `rows` and `cols`; text `lines` and `range` are inside the text of that side's state file); and a box over identical before and after pixels is demoted, with the warning "this box may not point at a real change", never silently. The pixel check reads the two pictures' `src` (a path, relative to the connector folder, or a `data:image/png;base64,` address) as 8-bit PNG files and compares the box's rectangle; pictures it cannot read give a warning that no pixel check ran, not a pass or a demotion. A demoted box means the connector did not earn level 3.

At every level, and for a connector with no level: two pairs asked A, B, A of one process give, byte for byte, the answers fresh processes give to A and B (case C17; `cocheck connector test` asks the edit and delete pairs).

The v1.2 fields are checked for shape at every level, as part of "the document is valid". How they degrade is printed as a warning, never graded: more than 50 issues (the page shows the first 50), issue text over 300 characters (the page cuts it there), and, for a connector whose `hello` declares `nothingChanged`, an empty `changes` for two state files that differ (the page will say nothing changed, so check it is a re-save and not a change the connector does not model). A `nothingChanged` in `hello` that is not `true` fails the hello check.

A connector that answers a change list without a `level` in hello is graded at the highest level a document can reach; the declared level is the cap. An answer that is not a `cocheck.changes/1` document is refused. An export connector is graded on its `export` answers: valid, the same text every run, a different text for each pair that changes, the same text for the pair that does not, an error for the malformed state, and text CoCheck can draw.

## One winner

When two installed connectors match the same call or subject, exactly one is used. The order, by what the manifest matched on: `matches.mcpTools`, then a `matches.subjects` template, then `matches.mcpServers`, then `matches.schemes`, then `matches.extensions` (the longest suffix wins, so `.notes.json` beats `.json`); a tie goes to the first folder by name. `cocheck connector doctor` and `cocheck connector test` print a warning for every overlap, naming the winner and the losers.

For files, CoCheck keeps which connector is enabled for each file type: at most one per type. The setting lives in the data folder, in `connector-types.json`; `cocheck connector list` shows, per type, the connectors that claim it, which one is enabled, and what CoCheck does with the file when none is; `cocheck connector enable <id> <ending>` and `cocheck connector disable <id> <ending>` change it. A file goes to the connector enabled for the longest ending it has; with none enabled, CoCheck draws it with its own readers (text, picture or fingerprint).

CoCheck's default rule, for any type the user has not set, works by file ending. CoCheck's own endings are the ones its own readers and renderers name: plain text, Markdown and csv (`.txt`, `.md`, `.csv`), pdf (`.pdf`), the Office files (`.docx`, `.xlsx`, `.xlsm`, `.pptx`, `.pptm`, `.ppsx`, `.ppsm`, which CoCheck itself does not read: the built-in connectors do) and pictures (`.png`, `.jpg`, `.jpeg`, `.gif`, `.heic`, `.tif`, `.tiff`, `.bmp`, `.webp`). A claimed ending counts as one of them when it is one of them, ends in one (`.notes.md`), or is the end of one. A built-in connector is enabled from the start for the types it claims. An installed connector that claims a type a built-in also claims, or one of CoCheck's own endings, starts disabled for it until the user enables it; for those types, installing a connector does not change what the reviewer sees until the user chooses it. Every other type goes to the connector that claims it, and when two claim it, to the first folder by name. That includes the text formats CoCheck shows by reading their content rather than their ending: code (`.py`, `.ts` and the rest), `.json`, `.rtf` and other text files. An installed connector that claims one of them is used for it from the moment it is installed, unless the user disables it. The user can always switch a type to any connector that claims it, or to none. A setting file CoCheck cannot read, or that is not valid, is ignored with a warning, and the default rule applies.

## Built-in connectors

Microsoft Excel, Word and PowerPoint ship with CoCheck as three connectors (`microsoft-excel`, `microsoft-word`, `microsoft-powerpoint`). Each is a folder with a manifest, speaks the same JSON lines, answers `cocheck.changes/1` at level 3 with `hello` declaring `"nothingChanged": true` (level 1 where no Office driver is built), and is held to the same checks as any connector. CoCheck's own code does not read, draw, order or open Office files. Their pictures come from the Office app printing each side to PDF. Their remaining privileges, the only things a built-in has that an outside connector does not (running on CoCheck's own Node is not one: see below):

- CoCheck's own code registers them, so they are enabled from the start for the types they claim, ahead of an installed connector (`src/connector/builtins.ts`, `src/connector/enabled-types.ts`).
- They ship inside the install (`src/connector/builtins.ts`).
- Their code is in `src/office/connector/`, and core imports nothing from it. The connector imports from core only the generic file lock (`src/file-lock.ts`) and these modules, listed with their reasons in `test/end-state-imports.test.ts`; each ends when it is published as a kit helper: `src/platform/index.ts` (which computer it is on, the installed Office version, starting and stopping Office), `src/timeline/render/pdf-helper.ts` (text and positions on a printed PDF page, and page crops), `src/formats/layer.ts` (the shape of a change list its readers fill in), `src/formats/files/layer.ts`, `src/formats/files/align.ts` and `src/formats/files/scan.ts` (the plain-file reader, line alignment, telling a presentation from other files), and `src/paths.ts` (comparing paths the same way on every computer).

### Node, and reserved ids

For any connector, built-in or installed, a `run` command whose first word is exactly `node` runs on CoCheck's own Node, never the `node` on PATH. Any other first word (an absolute path such as `/opt/tool/node`, `python3`, a relative path) is started as written, so a connector can ship its own interpreter.

The ids of the built-in connectors are reserved: `microsoft-excel`, `microsoft-word` and `microsoft-powerpoint`. This is the list of built-ins shipped with this release. An installed connector with one of these ids is never used or listed; the built-in answers for that id.
